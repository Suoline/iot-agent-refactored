# AgentCore-SVR 论文实验方案 v3

---

## 1. 审稿意见与新增隐私基线

审稿意见**明确提出了隐私方法消融**：

> AgentCore without SVR、AgentCore + generic masking、AgentCore + semantic placeholders。

因此，审稿人确实要求增加常见隐私保护方法的对比，但没有明确要求把差分隐私、同态加密或联邦学习实现成实验基线。v3 将审稿建议细化为两类常见、可在同一云 API 条件下公平实现的方法：

1. **Redaction/Masking（脱敏遮盖）**：敏感内容统一替换为 `[REDACTED]`。
2. **Opaque Pseudonymization/Tokenization（非语义假名化/令牌化）**：敏感内容替换为可逆但不携带设备类型的随机令牌，例如 `[ID_A7F3]`。

这两种方法分别代表“最大限度删除信息”和“保留指代关系但删除语义”。它们与 SVR 使用相同的 AgentCore、检测器、工具和模型，只改变替换策略，因此能直接回答语义占位符是否有价值。

以下方法不进入主实验：

| 方法 | 不作为主基线的原因 |
|------|------------------|
| 差分隐私（DP） | 主要保护聚合统计或数值查询，不能直接隐藏 entity ID；给控制参数加噪还可能改变实际动作。可作为精确传感器数值的未来扩展。 |
| 同态加密 / MPC | 普通闭源 LLM API 无法直接在密文上完成语义推理，需要修改云端 serving stack，与本文的即插即用设定不同。 |
| 联邦学习 | 主要解决训练数据不出端，不解决推理时 prompt 泄露。 |
| 纯本地 LLM | 同时改变模型能力、硬件和部署方式，不能作为隐私替换机制的公平消融。 |

## 2. 研究问题

只保留 3 个研究问题：

| RQ | 问题 | 对应实验 | 主指标 |
|----|------|----------|--------|
| RQ1 | SVR 相比无保护、通用脱敏和非语义假名化，能否更好地平衡直接隐私保护与任务效用？ | E1 | EPR、TLR、TSR |
| RQ2 | 敏感信息检测器和云端出口覆盖是否足以支撑上述隐私结果？ | E2 | precision、recall、F1、egress coverage |
| RQ3 | SVR 的本地处理和云 API 成本是多少？ | E3 | 本地 p50/p95、tokens/task、calls/task |

论文的核心结论应限制为：

> SVR 减少发送给云端 LLM 的直接敏感标识符和精确值，同时比通用遮盖或非语义假名化保留更多任务效用。

不得从本方案推出“完全匿名”“抵抗所有推理攻击”或“成本可忽略”等结论。

## 3. 威胁模型与隐私目标

### 3.1 攻击者与信任边界

- 云端 LLM/API provider 是 honest-but-curious：正常返回结果，但能够记录和分析收到的全部请求。
- 本地 home hub、SVR 模块、映射表和 Home Assistant 注册表可信。
- 所有离开 home hub 的 system/user message、tool result、生成代码请求、错误信息和重试上下文均属于云端可见数据。
- 攻击者看不到本地映射表和原始设备注册表。

### 3.2 保护目标

主目标是减少云端请求中的 **direct identifier/value leakage**，包括：

- 真实 entity ID、设备自定义名称；
- user/person ID 和人名；
- 房间或位置名称；
- 被定义为敏感的精确状态、传感器值和时间戳。

### 3.3 非目标

SVR 占位符会保留完成任务所需的设备类型、动作能力和指代关系，因此：

- 不保证隐藏设备类型；
- 不保证隐藏一次交互中出现的设备数量；
- 不保证抵抗语义推断、长期行为分析、请求时序或 token 长度侧信道；
- 不声称 session 刷新已经被实验证明可以阻止跨 session 链接。

这些内容在论文的 Limitations 中说明，不再为其建立独立主实验。

## 4. 数据集：新的 SVRBench-100

### 4.1 数据划分

只建立两个新集合：

| 子集 | 规模 | 用途 | 是否报告结果 |
|------|------|------|--------------|
| Dev-20 | 20 个任务，1 个开发家庭 | 调整 prompt、检测规则和任务判定器 | 否 |
| Test-100 | 100 个冻结任务，5 个测试家庭 | 所有论文主实验 | 是 |

开发家庭和测试家庭的实体名称、用户名称、房间名称和任务文本不重叠。开始 Test-100 前冻结 prompt、检测器、替换规则、任务 oracle 和统计脚本。

### 4.2 Test-100 构成

采用 `5 个家庭 × 5 个主类别 × 每格 4 个任务 = 100 个任务`：

| 主类别 | 数量 | 主要判定方式 |
|--------|------|--------------|
| Device Control（DC） | 20 | 目标设备与最终状态 |
| Command Chaining（CC） | 20 | 必要动作集合、顺序约束和禁止动作 |
| Information Retrieval（IR） | 20 | 结构化答案、集合 F1 或数值容差 |
| Persistence（PT） | 20 | 触发前不得执行，触发后在时间窗内执行 |
| Personalization（PR） | 20 | 是否正确使用冻结的用户偏好或安全回退 |

每个测试家庭包含 20 个任务，每类 4 个。每个任务只能有一个 `primary_category`，以避免分类结果重复计数。

### 4.3 任务设计要求

- 每个任务至少包含一种会进入云端上下文的敏感字段。
- medium/hard 任务加入同类型干扰设备，避免只靠设备类型即可猜中目标。
- 每个任务预先保存：`init_state`、`expected_actions`、`expected_final_state`、`expected_answer`、`forbidden_actions` 和 `sensitive_sources`。
- 所有系统使用相同的初始状态、工具、超时、最大调用次数和 token 预算。
- 模型超时、工具调用错误和不可解析输出计为失败；只有 API 服务中断或日志损坏可标记为 invalid。

### 4.4 敏感信息金标准

对 Test-100 运行时产生的全部 pre-transform 云请求建立敏感 span 金标准：

1. entity、user、room、state 和 timestamp 等结构化字段由模拟器通过独立 `provenance_id` 自动标记。
2. 用户自由文本中的人名、别名和隐式位置由两名标注者复核。
3. 金标准不能由 SVR 检测器的命中结果生成，否则漏检项会从分母消失。
4. 分歧在查看实验结果前解决并冻结。

## 5. 对比配置

所有配置使用完全相同的 AgentCore 架构、system prompt、工具描述、任务输入、模型参数和运行预算，只切换隐私处理层。

| 配置 | 隐私处理 | 示例 | 作用 |
|------|----------|------|------|
| C0 No Protection | 不替换 | `light.living_room_main` | 无保护效用上界、直接泄露基线 |
| C1 Redaction | 所有敏感项统一遮盖，不可逆 | `[REDACTED]` | 常见数据脱敏；隐私上界与效用下界参考 |
| C2 Opaque Tokenization | session 内随机、可逆、无设备类型语义 | `[ID_A7F3]`、`[VAL_B219]` | 常见假名化/令牌化基线，保留对象区分和往返映射 |
| C3 AgentCore-SVR | session 内可逆、保留必要类型语义 | `[LAMP_1]`、`[ROOM_1]` | 提出方法 |

公平性要求：

- C1、C2、C3 使用同一个敏感信息检测器，只改变被检出 span 的替换形式。
- C2 和 C3 使用相同生命周期的本地映射表，并在 session 结束后销毁。
- C2 的随机 token 长度固定，避免通过超长哈希人为增加 token 成本。
- C3 不保留真实房间名或 user-visible device name；只保留冻结的通用类别，例如 LAMP、SENSOR、ROOM。
- C1 只作为常见脱敏参考，不能用它的低效用单独证明 SVR 优越；最关键的语义消融是 C2 vs C3。

主对比为：

1. **C0 vs C3**：SVR 的总体隐私收益与效用代价。
2. **C2 vs C3**：保留设备类型语义是否提高任务成功率；这是论文最重要的机制消融。
3. **C1 vs C3**：与常见全遮盖方法的实用性对比，作为辅助结果。

## 6. 指标

### 6.1 直接隐私指标

对每个实际发往云端的请求 \(r\)：

- \(G_r\)：变换前 payload 中由金标准标出的敏感 span 数量；
- \(L_r\)：实际发送 payload 中仍以明文出现的敏感 span 数量。

**Egress Protection Rate（EPR，主隐私指标）**：

```text
EPR = 1 - ΣL_r / ΣG_r
```

**Task Leak Rate（TLR）**：

```text
TLR = 至少一个云请求发生明文泄露的任务数 / 总任务数
```

辅助报告：

- residual sensitive spans/task；
- 按 entity、person、room、state/value、timestamp 分字段的残留数量；
- 残留原因：检测器漏检或未经过统一 egress handler。

主隐私结果只统计 **outbound cloud requests**。云端响应回显和本地反匿名后的真实 ID 不混入 EPR。

### 6.2 任务效用

**Task Success Rate（TSR）**：任务全部适用断言通过且没有 `forbidden_actions` 的比例。

报告：

- 总体 TSR；
- 五个主类别的 TSR；
- C0−C3 的配对 TSR 差值，即 privacy tax；
- C3−C2 的配对 TSR 差值，即 semantic utility gain。

不再使用“三次任一成功”作为主结果。若报告 pass@3，只能放附录并明确其额外调用成本。

### 6.3 检测器与出口覆盖

- token/span-level precision、recall、F1；
- 按敏感字段分类的 recall；
- `egress coverage = 经过统一隐私处理器的云请求数 / 全部云请求数`。

Egress coverage 必须为 100%。如果不能达到 100%，应先修复系统，或降低论文的隐私声明并报告旁路请求比例。

### 6.4 成本

- sanitize + de-anonymize 的本地 p50/p95 延迟；
- 本地内存增量；
- input/output tokens per task；
- LLM calls per task；
- 可选：美元/task 和美元/successful task。

不把端到端延迟全部归因于 SVR；云模型推理和多轮调用必须与本地替换耗时分开。

## 7. 实验协议

### E0：运行前实现检查（不作为论文主实验）

在正式跑 Test-100 前必须通过：

1. system/user message、tool result、code-generation request、error/stack trace 和 retry context 全部经过同一 egress handler。
2. C2/C3 的 original→placeholder→original 往返正确率为 100%。
3. 不同原始值不会映射到同一占位符。
4. 用户输入中的 placeholder-like 文本先转义。
5. LLM 返回未知占位符时拒绝执行或触发受控重试，不能直接绑定设备。

这些属于实现正确性门槛，用单元测试和集成测试验证，不需要单独占用论文结果表。

### E1：隐私—效用主实验（RQ1）

#### 运行矩阵

- 主模型：C0/C1/C2/C3 × Test-100 × 3 次独立运行，共 1200 次任务执行。
- 复现模型：C0/C2/C3 × Test-100 × 3 次独立运行，共 900 次任务执行。
- 合计 2100 次，不含预注册的 invalid-run 替换。

主模型可使用论文目标商业 API；复现模型优先选择一个固定 checkpoint 的开放权重 instruct 模型。必须记录准确模型 ID、调用日期、temperature、top_p、max tokens、SDK 版本和 prompt hash。

#### 流程

1. 每次任务开始前重置并验证家庭状态。
2. 随机交错运行各配置，避免 API 时间漂移只影响某个方法。
3. 记录每个云请求的 pre-transform payload、实际 outbound payload、response、tool action 和最终环境状态。
4. 用同一任务 oracle 判断 TSR，用冻结敏感金标准计算 EPR/TLR。
5. 失败任务不得因“模型表现不好”任意重跑。

### E2：检测器有效性与残留泄露（RQ2）

在 Test-100 的全部真实 pre-transform outbound payload 上评估检测器：

1. 与冻结敏感 span 金标准比较，报告总体 precision/recall/F1。
2. 按 entity、person、room、state/value、timestamp 分字段报告 recall。
3. 列出主要 false negative 类型，例如未注册别名、自由文本人名、Unicode、嵌套 JSON 和生成代码中的 ID。
4. 将 C3 的残留明文逐条归因到检测器漏检或 egress 旁路。

输出一张检测器表和一个简短的错误类型表即可。不再建立 Privacy-400，也不做注册表/关键词/正则的全部组合消融。

### E3：系统开销（RQ3）

#### 本地开销

从 E1 日志抽取短、中、长三档真实 payload，每档随机选择 100 个 payload；在目标边缘设备上分别重放 C1/C2/C3 的 sanitize 和 de-anonymize，各重复 100 次。

报告：

- p50/p95 本地延迟；
- 不同 payload 长度下的延迟；
- 映射表内存增量。

#### 云端开销

直接从 E1 日志计算：

- input/output tokens per task；
- calls per task；
- wall-clock per task 仅作辅助；
- 如能获得价格，报告 cost per successful task。

结论使用中性表述：SVR 的本地替换成本是多少、token 是否增加以及增加多少，不预设“negligible”或“acceptable”。

## 8. 统计方法

1. 每个配置对每个任务独立运行 3 次，主表报告任务级平均成功率。
2. 对 C0 vs C3、C2 vs C3 做**按任务配对 bootstrap**，重采样单位为任务，报告 TSR 差值和 EPR 差值的 95% CI。
3. 总体结果为主；五分类结果主要用于解释失效模式，不对每个小类别堆叠大量显著性检验。
4. 同一任务的 3 次运行不能当作 3 个独立任务扩大样本量。
5. 主文不报告 pass@3；所有配置保持相同单次运行口径。

无需在主方案中加入混合效应模型、TOST 或 MDE。若最终结果处于临界状态，可在统计分析阶段再补充，但不把它们预先扩展成独立实验。
