# SAE 记忆系统：实验设计与测试套件（v3）

> v3 基于 `memory-system-design-v4.md` 对 v2 做了修订，并补齐了评审中发现的覆盖缺口。相较于 v2，主要变化如下：
> 1. **补齐了四个真实的设计主张缺口**：`delete`/隐私操作（F7）、*成功* 的 `merge` + coverage_proof + 维护回滚（F6）、“瞬时状态不得持久化”这一核心原则（G5），以及查询任务的 0.45 阈值分层（新增 H 类）。
> 2. **拆分治理分支**：A4（模糊文本 → 重采样）与 A6（非模糊老化 → stale→archived），因此 §12.1 的两条诊断分支都能被测试。
> 3. **新增两个基线**：B4 全量历史 / 大上下文（不做检索）作为缺失的对照组，用于验证“你是不是只是因为上下文更多才赢”的主张（§6.3、表 4）；B5 为已发表系统的类比基线（Generative Agents 风格的打分检索），避免只和自建的稻草人系统比较。
> 4. **把整套内容完整写清楚**：§5 现在为全部 36 个场景提供了在具体冻结实体注册表（§4）上的、完全指定的确定性交互脚本。这就是“全部测试用例 / 测试集”交付物。
> 5. **强化了统计方案与外部依赖说明**：将指标分成主要指标与次要指标层级（主要指标 N≥30），同时把真实 HA 回放 / 真实使用日志缓解方案降级为显式的条件项 / 未来工作，而不再默认其一定可用。
> 场景总数：**36** = A6 + B6 + C4 + D3 + E3 + F7 + G5 + H2。

## 1. 概览

本文档是用于验证智能家居 Agent 的 **Structured Memory + Lifecycle Closure**（结构化记忆 + 生命周期闭环）v4 架构的实验设计与具体测试套件。被测试的核心贡献包括：

1. **记忆过期机制**：半衰期衰减、硬过期 / 时间窗口过期、生命周期状态机（v4 §5）
2. **记忆更新操作**：完整的 add / merge / revise / invalidate / split / delete 集合，以及 provenance 与 coverage_proof（v4 §7）
3. **置信度校准**：非对称反馈、Memory Worth 分层、使用阈值（v4 §6）
4. **失活记忆治理**：双分支检测（重采样 vs 老化淘汰）+ 重采样（v4 §12.1）
5. **检索 / 规划门控**：候选隔离、注册表权威、歧义门（v4 §8、§11）

面向评审的目标：
- 预注册的指标，并基于命名 trace 字段给出显式公式（§8）
- 通过消融实验隔离每种机制的边际贡献（§7）
- 从无状态到大上下文再到已发表系统类比的基线阶梯（§6）
- 可审计的“主张↔场景↔RQ↔指标”覆盖矩阵，确保 v4 的设计主张零遗漏（§14）
- 完全指定、冻结、双标注的确定性测试脚本（§5）

## 2. 核心研究问题

**RQ1 — 记忆过期。** 与没有过期机制的系统相比，时间感知型管理（衰减 + 硬过期 + 时间窗口有效性）是否能减少过时记忆召回，并保持任务成功率？

**RQ2 — 记忆更新。** 结构化的更新操作（merge / revise / invalidate / split / delete）是否比朴素覆盖写入更能维持记忆一致性与来源可追溯性？

**RQ3 — 置信度校准。** 非对称执行反馈 + Memory Worth 分层 + 使用阈值，是否能提升可靠性并减少澄清开销？

**RQ4 — 失活记忆治理。** 双分支的失活记忆检测 + 重采样，是否能在不丢失有价值信息的前提下提升存储效率与检索精度？

**RQ5 — 端到端性能与成本。** 集成系统是否能在任务成功率以及用户满意度的操作化代理指标（澄清负担、不安全动作规避、偏好匹配）上优于各类基线，且 **上下文成本可接受**，也就是并非仅仅因为比大上下文基线消耗了更多 token 才取得优势？

> RQ5 不是人类受试实验；这里的 N≥30 / 20 次运行是对 LLM 采样重复。这里“用户满意度”按 §6.4 的三个可计算代理指标进行操作化：CB、UAA、PM。

## 3. 场景设计维度

**时间动态：** 静态（能力、布局）· 演化型（偏好、别名）· 情景型（任务结果、临时规则）。

**歧义级别：** 无歧义（“打开卧室顶灯”）· 中等歧义（“打开小灯”，需要别名解析）· 高歧义（“开灯”，需要房间 / 时间 / 使用上下文）。

**极性：** 正向（系统应执行 / 回忆）· 负向（系统应保持沉默、发起澄清或拒绝编造）。G 类以及 A/C/H 中的负向分支会显式测试极性。

## 4. 冻结测试集 —— 世界模型 `world_model/v1.json`

(a) 名称重叠 / 存在歧义的设备，使消歧并不平凡；

(c) 可用于 D/E/F 场景的失败注入与变化注入实体。

## 5. 测试套件 —— 36 个确定性场景脚本

### 5.1 脚本格式

每个场景都是一个冻结的有序步骤列表。每一步只会是以下几类之一：

- **`say`** —— 用户在 `t` 时刻的发言（相对于场景开始时间 t0）。
- **`event`** —— 来自 §4.4 的世界变化 / 失败注入，或一次时钟推进。
- **`expect_action`** —— 系统应输出的真实动作（`{service, entity, args}`），若正确行为应为静默则为 `∅`。
- **`expect_clarify`** —— 真实正确行为应该是发起澄清问题（负向 / 歧义场景）。
- **`expect_memory`** —— 步骤之后断言的真实记忆状态：memory_type、关键字段以及生命周期 `status`（用于 SRR / UC / DMR 评分，独立于系统自报）。

评分使用字段：`expect_action`↔TSR / WDR / PM，`expect_clarify`↔CB / CE，`expect_memory.status`↔SRR / UC，安全标记↔UAA。每个场景都带有 `RQ` 和 `Planner` 标记（RQ1–RQ4 使用 oracle；RQ5 使用 agent，见 §9）。时间记法 `t0+Nd HH:MM` 使用仿真时钟（§10 harness）。

每个场景进行双标注；若标注不一致，则交由第三位标注者裁定；最终报告 Cohen's κ（§12）。

### A 类 —— 别名演化与治理（6）—— RQ1、RQ2、RQ3、RQ4

**A1 — 别名提交与回忆。** *(Planner: oracle；RQ3)*
1. `say` t0 09:00 “以后把书房台灯叫小书灯” → `expect_memory`：alias(小书灯→`light.study_desk`)，`source=user_explicit`，`status=active`，`conf=0.90`。
2. `say` t0+1d 20:00 “打开小书灯” → `expect_action` `light.turn_on(light.study_desk)`；`expect_memory`：同一别名，`positive_hits=1`。
- 检查点：显式别名应立即进入 active（v4 §11），能正确回忆，并在正向命中后得到强化。

**A2 — 别名重绑定 / 取代。** *(oracle；RQ2)*
1. `say` t0 “卧室灯就是卧室顶灯” → alias(卧室灯→`light.bedroom_ceiling`) active。
2. `say` t0+3d “以后卧室灯指床头灯” → `expect_memory`：旧别名 `status=superseded`，`superseded_by=new`；新 alias(卧室灯→`light.bedroom_bedside`) active，`conf=0.95`。
3. `say` t0+3d “开卧室灯” → `expect_action` `light.turn_on(light.bedroom_bedside)`。
- 检查点：修订 / 取代、来源链、不能再召回旧绑定。（UC 场景）

**A3 — 竞争别名与置信度消歧。** *(oracle；RQ3)*
1. `say` t0 “书房台灯叫小书灯” → alias A active（conf 0.90）。
2. `event` t0+1d：行为推断得到别名 B（“台灯”→`light.study_ceiling`），写入为 candidate（`source=user_behavior`，`conf=0.65`，`status=candidate`）。
3. `say` t0+2d “开台灯” → top1（A，active）与 candidate B 比较：candidate 必须被排除出可用集合；若剩余歧义边界小于阈值，则 `expect_clarify`，否则对 A 执行动作。
- 检查点：candidate 隔离（§11）、歧义门（§8.1 step 7）。

**A4 — 失活记忆：模糊文本 → 重采样。** *(oracle；RQ4)*
1. `event` t0：预置 alias(小书灯→`light.study_desk`)；其 `natural_text` 故意模糊（“那个灯”），`access_count=0`，`half_life=365d`。
2. `event` t0+400d：维护任务运行 → `is_dead=true`（`access_count==0 ∧ age>half_life`）。诊断：文本模糊（高 embedding entropy）→ 走 **resample** 分支：LLM 将 `natural_text` 重写为更具体表述，`resampled=True`，`last_accessed` 重置。
3. `say` t0+401d “开小书灯” → `expect_action` 作用于 `light.study_desk`；`expect_memory`：状态恢复为 `active`（被 revive）。记入 RRR。
- 检查点：§12.1 分支 2 的重采样、RRR。

**A5 — 用户纠正 → 负向命中 + 反思。** *(oracle；RQ2、RQ3)*
1. `say` t0 “开小书灯”（别名已 active）→ 动作作用于 `light.study_desk`。
2. `say` t0 “不对，不是这个灯，是书房顶灯” → `expect_memory`：alias(小书灯) `negative_hits+1`，置信度下降（`α_neg=0.20`），状态变为 `stale/conflicted`；写入新的纠正别名或 reflection（`failure_type=wrong_device`）。之后再次回忆时必须优先使用纠正后的目标。
- 检查点：非对称负反馈（§6.2）、reflection（§10.2）。（UC 场景）

**A6 — 失活记忆：非模糊老化 → stale→archived。** *(oracle；RQ4) —— v3 新增，与 A4 互补*
1. `event` t0：预置 alias(客厅落地灯→`light.living_floor`)；`natural_text` 已经足够具体，`access_count=0`，`half_life=365d`。
2. `event` t0+400d：维护任务运行 → `is_dead=true`。诊断：文本 **不是** 模糊文本 → 走 **content-aging** 分支（§12.1 step 3）：状态 `active→stale→archived`；Memory Worth 较低 → 成为清理候选。
3. `say` t0+401d “开客厅落地灯” → 允许 archived 的召回失效；`expect_action` 应回退到 HA 注册表匹配（设备仍存在），从而验证 archived 不会阻断执行，且老化不等于重采样。`expect_memory`：别名状态保持为 `archived`（而非 resampled）。
- 检查点：§12.1 分支 3 的 aging，与 A4 区分；DMR。

### B 类 —— 偏好与习惯形成（6）—— RQ1、RQ3

**B1 — 单次观察只应停留在 candidate。** *(oracle；RQ3)*
1. `event` t0 20:00：观察到用户把 `climate.bedroom_ac` 设为 24°C 一次 → 习惯候选项，`status=candidate`，`source=user_behavior`。
2. `say` t0+1d “睡觉了” （睡眠例程）→ `expect_action` **不得** 自动应用 24°C（candidate 不可直接使用）。`expect_memory`：candidate 保持不变。
- 检查点：candidate 隔离防止过早自动化（§11）。

**B2 — 7 天内 3 次 → 习惯晋升。** *(oracle；RQ3)*
1. `event` t0 / t0+2d / t0+4d 20:00：相同行为 24°C 共出现 3 次，且没有反例。
2. `event` t0+4d maintenance → 习惯（卧室睡前 24°C）从 `candidate→active`（7 天 / 3 次规则，§11）。
3. `say` t0+5d “睡觉了” → `expect_action` 包含 `climate.set_temperature(bedroom_ac,24)`。
- 检查点：晋升门槛。

**B3 — 显式陈述 → 立即 active。** *(oracle；RQ3)*
1. `say` t0 “我睡觉时喜欢空调 26 度” → 偏好立即 active（`conf=0.90`，来源 explicit）。
2. `say` t0 “睡觉了” → `expect_action` 设为 26。
- 检查点：显式输入路径优先于行为晋升路径。

**B4 — 偏好撤销。** *(oracle；RQ1)*
1. `say` t0 “睡觉时把空调设成 26 度” → 偏好 active。
2. `say` t0+3d “以后睡觉别自动调空调了” → `expect_memory`：偏好状态变为 `superseded/expired`。
3. `say` t0+3d “睡觉了” → `expect_action` **不得** 设置温度。（负向动作检查）
- 检查点：时间窗口 / 显式失效会移除其对规划的影响。（UC 场景）

**B5 — 长期矛盾行为 → 习惯衰减 / 被取代。** *(oracle；RQ1)*
1. `event` t0：习惯（睡前 24°C）已 active。
2. `event` t0+1d..t0+10d：观察到 5 次用户改为设置 27°C。
3. `event` t0+10d maintenance → 旧习惯变为 conflicted，随后被新习惯（27°C）取代。
4. `say` t0+11d “睡觉了” → `expect_action` `set_temp 27`。
- 检查点：由行为驱动的 supersession，以及在矛盾下的衰减。

**B6 — 高 MW 偏好用于高风险任务。** *(agent；RQ3)*
1. `event` t0：偏好（睡前锁大门）具有 `MW>0.8`（正向命中很多、`conf>0.85`），来源 explicit + 多次验证成功执行。
2. `say` t0+30d “睡觉了” → 涉及安全相关的锁门动作。依据 §6.3，MW>0.8 “可在高风险场景直接使用”：`expect_action` 为 `lock.lock(front_door)`，并且 **无需** 额外澄清；而一条新鲜但低 MW 的偏好（对照组）则应要求确认。
- 检查点：MW 分层是否真正改变门控行为，而不仅仅是记账。对比其与对照组的 CB。

### C 类 —— 临时规则与时间窗口有效性（4）—— RQ1、RQ3

**C1 — 一周临时规则到期。** *(oracle；RQ1)*
1. `say` t0 “这周客厅灯晚上 7 点自动开” → 生成规则，`valid_until=t0+7d`，状态 active。
2. `event` t0+3d 19:00 → `expect_action` `light.turn_on(living_ceiling)`（在有效窗口内）。
3. `event` t0+9d 19:00 → `expect_action ∅`；`expect_memory`：规则状态为 `expired`（`valid_until` 已过）。到期后不得执行。
- 检查点：`valid_until` 硬窗口约束。

**C2 — 明确日期范围的节假日自动化。** *(oracle；RQ1)*
1. `say` t0 “国庆假期（t0+10d 到 t0+17d）每晚开氛围灯” → 设置 `valid_from / valid_until`。
2. `event` t0+5d 20:00 → `∅`（早于窗口）；`event` t0+12d 20:00 → 执行 `living_ambient`；`event` t0+20d 20:00 → `∅`，状态 expired。
- 检查点：同时校验 `valid_from` 与 `valid_until`，包括边界。

**C3 — 通过置信度衰减实现软过期。** *(oracle；RQ1)*
1. `event` t0：低重要度偏好，`conf=0.72`，`half_life=90d`。
2. `event` t0+180d：`effective_confidence = 0.72·2^(-2)≈0.18 < control threshold 0.70`。
3. `say` t0+181d 相关任务 → `expect_clarify`（低于阈值）而不是静默使用；`expect_memory`：状态 `active→stale`（`eff_conf<0.45`）。
- 检查点：通过 `effective_confidence` 实现软过期（§5.2），以及阈值门控（§6.4）。

**C4 — needs_verification（MW 0.2–0.4）在使用前必须交叉验证。** *(oracle；RQ1、RQ3)*
1. `event` t0：一条 MW 在 0.2–0.4 区间的记忆（负向命中较高）→ 被标记为 `needs_verification`。
2. `say` t0+1d 依赖该记忆的任务 → `expect_clarify` / 交叉校验，而不是静默执行。
- 检查点：§6.3 中可疑层级的行为。

### D 类 —— 设备注册表变化（3）—— RQ1、RQ2

**D2 — 能力变化 → 依赖例程变 stale。** *(oracle；RQ2)*

### E 类 —— 例程与复合任务规划（3）—— RQ3、RQ5

**E1 — 观影模式复合任务。** *(agent；RQ5)*
1. `say` t0 “定义观影模式：关客厅顶灯、开氛围灯、关窗帘” → routine(观影模式) active，包含 3 个步骤。

**E2 — 含安全动作的例程需要确认。** *(agent；RQ5)*
1. `say` t0 “睡前模式：关全屋灯并锁大门” → routine active；其中 lock 步骤为安全相关动作。
2. `say` t0+1d “睡前模式” → 对灯的动作正常执行；lock 步骤需门控：`expect_clarify`，在执行 `lock.lock` 前要求确认（安全阈值 0.85，§6.4）。`safety_gated=true`。（UAA 场景）
- 检查点：安全层级的确认门控。

**E3 — 失败 → 反思 → 后续规划避开失败路径。** *(agent；RQ3、RQ5)*

2. `say` t0+2d 22:05 再次说 “睡前模式” → `expect_action`：灯的步骤仍执行，lock 步骤现在应改为告警 / 提示手动处理，而不是盲目重试（说明 reflection 被使用）。
- 检查点：执行闭环 —— reflection 避免重复进入失败路径（§10.2）；同时与 F3/F4 一起交叉验证 ripple isolation（只惩罚 lock 步骤，不影响灯）。

### F 类 —— 冲突、级联、合并、拆分与删除（7）—— RQ2、RQ4

**F1 — 特征吸收告警 → 特化（拒绝合并）。** *(oracle；RQ2)*
1. `event` t0：存在 alias(客厅灯→`light.living_floor`) 以及 fact(客厅顶灯→`light.living_ceiling`)。
2. `event` t0+1d maintenance 尝试 merge（主体重叠：客厅灯 ⊃ 客厅顶灯）→ §7.3 触发 **feature-absorption warning**：不得合并；转而创建 `MemoryEdge` 的 specialize / generalize 关系。`expect_memory`：两条记录都保留，edge 存在，且没有 merged record。
- 检查点：absorption warning、specialize edge。（负向 merge 分支）

**F2 — 两条高置信事实冲突 → conflicted + clarify。** *(oracle；RQ2)*
1. `say` t0 “小书灯是书房台灯” （`conf=0.90`）。
2. `say` t0+1d（另一会话）“小书灯是书房顶灯” （`conf=0.90`）→ §7.2 两条高置信冲突 → `expect_memory`：两条记录均为 `conflicted`。
3. `say` t0+1d “开小书灯” → `expect_clarify`（问是哪一个）。
- 检查点：冲突闭环、对 conflicted 状态触发澄清。

**F3 — 负向涟漪传播。** *(oracle；RQ4)*
1. `event` t0：预置记忆图 —— episode(lock task) ——edge dist1→ location(hall) ——edge dist2→ layout_relation。均为 active。
2. `event` t0+2d `evt_lock_jam` → lock task 失败 → 对 episode 施加 direct_penalty；传播惩罚 = `direct·0.3^d`，适用于 `d≤2`。`expect_memory`：dist-1 受到 0.3× 惩罚，dist-2 受到 0.09× 惩罚，dist-3（一个诱饵边）**不变**。
- 检查点：ripple decay `0.3^d`，`max_distance=2`（§7.4）。

**F4 — 正向命中不会传播（隔离性）。** *(oracle；RQ4)*
1. 相同的图结构，但在 t0+2d lock task **成功** → 只有被使用的 episode 的 `positive_hits+1`。
2. `expect_memory`：邻居记忆（dist 1、2）的 `positive_hits` 保持不变。
- 检查点：正向隔离 —— 成功不会污染邻域（§7.4）。与 F3 成对出现。

**F5 — 过宽记忆 → split。** *(oracle；RQ2)*
1. `event` t0：存在一条过宽 alias(客厅灯→匹配 `living_ceiling ∨ living_ambient ∨ living_floor`)，导致反复出现部分匹配 / 歧义。
2. `event` t0+1d maintenance 检测到频繁部分匹配 → 执行 **split**，拆成更细粒度记录（按实体拆分），并创建 specialize edges。`expect_memory`：原记录被取代，至少 2 条更细的新记录 active。
3. `say` t0+1d “开客厅顶灯” → `expect_action` 应干净地解析到 `light.living_ceiling`。
- 检查点：§7 中的 `split` 操作（split 后 partial-match rate 应下降）。

**F6 — 成功 merge + coverage_proof + rollback。** *(oracle；RQ2) —— v3 新增*
1. `event` t0：两条记录对象 **完全等价**（来自两个 session 的 alias 小书灯→study_desk）→ §7.3 允许 merge。`expect_memory`：生成单条 merged 记录，`merged_from=[both]`，记录 `coverage_proof`，并保留合并后的 `evidence_refs` 并集。
2. `event` t0+1d：注入一次 **遗漏 coverage_proof** 的 merge → maintenance job（§7.3 “否则回滚此次合并”）会 **回滚** 这次错误合并。`expect_memory`：错误 merge 被回退为两条独立记录。
- 检查点：正向 merge 路径 + coverage_proof + rollback（此前只有 F1 的负向分支）。

**F7 — 隐私删除。** *(oracle；RQ2) —— v3 新增*
1. `say` t0 “记住我常去健身房” → 偏好 active（并被 embedding 建索引）。
2. `say` t0+2d “把我去健身房这件事忘掉” → 执行 `delete` 操作（§7）：逻辑删除，并从 Chroma 索引移除。`expect_memory`：状态为 `deleted`，但审计事件仍保留（`memory_events.jsonl`）。
3. `say` t0+2d 发起一个原本会召回它的查询 → `expect_action ∅` / 不得召回；已删除内容不得再次浮现。
- 检查点：`delete` 操作（最后一个未被测试的更新操作）+ 索引移除 + 不再复现。
  同时如果被标记为敏感内容，也覆盖 §12.1 中 `sensitive=true → needs_review` 的路径。

### G 类 —— 负向对照与冷启动（5）—— RQ1、RQ4、RQ5

**G1 — 冷启动，不得编造。** *(agent；RQ5)*

**G3 — 注册表覆盖过时记忆。** *(oracle；RQ1)*

**G4 — 低置信度不得直接执行。** *(oracle；RQ3)*
1. `event` t0：一条由 `llm_inference` 得到的设备绑定 candidate，`conf=0.45`。

- 检查点：使用阈值 + candidate 隔离。

**G5 — 瞬时状态不得进入长期记忆。** *(oracle；RQ1、RQ4) —— v3 新增*
1. `event` t0 20:00：观察到 `light.living_ceiling` 当前处于开启状态（`ha_state_observation`）。
2. `event` t0+1d maintenance → `expect_memory`：**不应** 为该瞬时 on-state 创建长期 `MemoryRecord`（v4 §3 原则：当前状态不进入长期记忆；只属于 perception）。
3. `say` t0+2d 09:00 “客厅灯之前是不是开着” → 系统可以基于短期 perception 回答（如果还可用），但不得持久化出一条 `stable_state_fact` 宣称它是开着的，也不得基于此为未来动作做假设。`expect_memory`：不存在持久化状态事实。

### H 类 —— 查询任务与阈值分层（2）—— RQ3 —— v3 新增

该类覆盖 v2 中缺失的查询分层（0.45 阈值，§6.4）。

**H1 — 查询任务在 0.45 阈值层可容忍更低置信度。** *(oracle；RQ3)*
1. `event` t0：一条偏好 / 状态记忆，`effective_confidence ≈ 0.5`（介于 0.45 与 0.70 之间）。
2. `say` t0+1d “卧室空调设的多少度” （查询而非控制）→ 阈值 0.45 → `expect_action`：可以回答，但必须带不确定性提示；**不应** 发起澄清。

**H2 — 查询层与控制层的边界对比。** *(oracle；RQ3)*
1. 使用同一条 0.5 置信度记忆。
2. `say` t0 “空调几度” （查询）→ 可回答（0.45 层）；`say` t0 “按我喜欢的温度设空调” （控制）→ `expect_clarify`（0.70 控制层未达标）。同一条记忆、两种层级、两种行为。
- 检查点：§6.4 的阈值表是否按任务类型生效，这是差异化主张的直接验证。

### 5.2 场景数量与构建协议

总计 **36** 个场景：A(6) + B(6) + C(4) + D(3) + E(3) + F(7) + G(5) + H(2)。构建协议如下：
- 每个场景均由独立于实现的标注者编写成上述冻结步骤列表，并绑定到 `wm-v1`。
- 所有时间相关步骤均使用仿真时钟（§10），因此半衰期 / 过期逻辑可被即时测试。
- 所有 `expect_*` 真值字段都进行双标注；有分歧时交由第三位标注者裁定；最终报告 κ。
- 负向场景（G 类，以及 A5 / B1 / B4 / C1–C4 / F1 / F2 的负向分支）都带有 `expect_action=∅` 或 `expect_clarify` 的真值，因此“正确静默”可被评分。

## 6. 基线

| ID | 基线 | 描述 | 回答的问题 |
| --- | --- | --- | --- |
| **B0** | 无状态 | 无记忆；每轮只使用当前话语 + HA 注册表。 | 记忆本身是否有价值 |
| **B1** | 仅 RAG（top-k） | 过去话语进入向量库；做 top-k 检索；无结构、无生命周期。 | 结构化是否有价值 |
| **B2** | 结构化，但无生命周期 | 结构化事实元组，但永远 active；无过期 / 置信度 / 治理。 | 生命周期是否有价值 |
| **B3** | 结构化 + 静态置信度 | 有来源先验置信度，但无衰减、无反馈更新。 | 动态置信度是否有价值 |
| **B4** *(新增)* | 全量历史 / 大上下文 | 将全部交互历史直接塞入 planner prompt，**不检索、无结构**。上下文无限增长。 | “是不是只是上下文更多？” |
| **B5** *(新增)* | 已发表系统类比 | Generative Agents 风格的打分检索（recency + importance + relevance），无生命周期 / 过期 / 治理。代表 Mem0 / GA 一类已有工作。 | 与真实先验工作相比如何 |
| **Ours** | SAE Memory v4 | 完整系统：结构 + 生命周期 + 非对称反馈 + 治理。 | — |

**为什么必须要有 B4。** §6.3 / 表 4 / §13 都声称 Ours 不是因为消耗更多 token 才赢。这个主张只有在与大上下文对照组比较时才可证伪。B4 就是这个对照组：如果 Ours 以远少于 B4 的 `prompt_tokens` 达到相同或更高的 TSR，就说明起作用的是记忆结构，而不是 token 预算。B4 同时也测试扩展性（随着历史增长，其 prompt 会不断膨胀；Context Efficiency 应随仿真时间显著恶化）。

**为什么必须要有 B5。** B0–B3 都是内部构造的基线阶梯，评审者会问为什么不与已发表的记忆系统比较。B5 近似 Generative Agents 的检索打分机制（也可作为 Mem0 类 extract-merge 记忆的替身），使 Ours 的改进不只是相对于稻草人系统，而是相对于已有工作。

> 所有基线都运行在 **相同的 planner mode**（§9）、**相同的冻结 `wm-v1`**（§4）、相同的 LLM / temperature、相同的 embedding model、相同的场景脚本与时钟之上。唯一变化的是记忆子系统。B4 的唯一区别是向 planner 提供原始全量历史，而不是检索后的记忆包。

## 7. 消融实验

每个消融都只移除 Ours 中的一个机制，从而隔离其边际贡献。所有消融都在 **oracle planner**（§9）下运行完整 36 场景套件；报告指标差异及 95% 置信区间。

| 消融项 | 移除的组件 | 预期退化 | 诊断场景 |
| --- | --- | --- | --- |
| **−Decay** | 半衰期衰减（`eff_conf = raw conf`） | 过时召回上升 | C3、A4 / A6、图 2 |
| **−AsymFeedback** | 非对称命中更新（`α_pos=α_neg`） | 纠错更慢，校准能力下降 | A5、E3、图 1 |
| **−Governance** | 失活记忆检测 + 重采样 | 失活记忆率上升，长期精度下降 | A4、A6、G2 |
| **−CandidateGate** | candidate 隔离（所有候选都视为 active） | 过早推断导致错误设备执行增多 | B1、A3、G4 |
| **−ConflictHandling** | 冲突检测（改成朴素覆盖） | 更新正确性下降，证据丢失 | A2、F2 |
| **−FeatureAbsorption** | §7.3 的吸收告警（总是 merge） | 过度泛化上升 | F1、F5、F6 |
| **−Ripple** | 负向级联传播 | 系统性恢复更慢 | E3、F3 |
| **−Split** *(新增)* | 禁用 §7 的 split（保留过宽记录） | 部分匹配 / 歧义错误上升 | F5 |

## 8. 评估指标

> **原则：所有指标都预先注册为基于命名 trace 字段（§11）的公式。** v1 中关于 SRR 分母、CE 加权、MP 中“helpful”判定的三处模糊点，在 v2 中已被解决，这里继续沿用。

### 8.1 主要指标（N≥30）

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| **TSR** | 最终设备状态与真值意图一致的任务比例 | ↑ |
| **SRR** | 可用集合中包含 expired / superseded 记忆的检索步骤比例 | ↓ |
| **WDR** | 控制类任务被路由到错误实体的比例 | ↓ |
| **CE** | 在保持准确率前提下的澄清减少幅度（公式见 §8.5） | ↑ |
| **UC** | 在纠正之后，旧记忆被失效且新记忆被使用的比例 | ↑ |

### 8.2 校准与治理指标（N≥20）

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| **ECE** | 期望校准误差：预测 `eff_conf` 与实际成功率之间的偏差（M=10 bins） | ↓ |
| **DMR** | 超过半衰期且从未被访问的记忆比例 | ↓ |
| **RRR** | 被重采样的记忆在下一个维护周期中再次被召回的比例 | ↑ |
| **MP** | 已提交记忆中，之后被“有帮助地”使用的比例（确定性规则见 §8.5） | ↑ |

### 8.3 成本与效率（按任务记录，按系统汇总）

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| **端到端延迟** | 从 utterance 到动作决策的时间（ms） | ↓ |
| **检索延迟** | 检索阶段耗时（ms） | ↓ |
| **维护成本** | 每个仿真日运行一次维护任务所消耗的时间 + token | ↓ |
| **Prompt Token Count** | 每个任务输入给 planner LLM 的 token 数 | ↓ |
| **Active Memory Count** | 随时间变化的 active / stale 可检索记忆规模 | — |
| **Context Efficiency** | `TSR ÷ mean prompt_tokens × 1000` | ↑ |

> Context Efficiency 是和 B4 做比较时的核心指标：在远少的 token 下达到与 B4 相近的 TSR，说明起作用的是结构，而不是预算。

### 8.4 RQ5 的用户满意度代理指标

| 代理指标 | 定义 | 来源 | 方向 |
| --- | --- | --- | --- |
| **Clarification Burden (CB)** | 每个任务平均需要几轮澄清 | trace `clarification_turns` | ↓ |
| **Unsafe-Action Avoidance (UAA)** | 在安全任务中，低于 0.85 置信度的动作被门控拦下的比例 | safety log | ↑ |
| **Preference Match (PM)** | 最终选择的动作与标注偏好一致的比例 | scenario GT | ↑ |

### 8.5 操作化定义（基于 §11 trace 的公式）

记号：一次 run 中的任务集合为 `t∈T`；任务中的检索步骤集合为 `s∈S_t`；每一步返回可用集合 `R_s`（状态 ∈ `{active, usable-stale}`）。

- **TSR** = `(1/|T|)·Σ_t 1[final_device_state(t)==ground_truth_state(t)]`，按标注目标做精确匹配。
- **SRR** = `Σ_t Σ_{s} 1[∃ m∈R_s : true_status(m,t)∈{expired,superseded}] / Σ_t |S_t|`。
  其中 `true_status` 由仿真时钟 + `expect_memory` 标注得到，独立于系统自报状态。
- **WDR** 针对控制任务 `T_ctrl`：`(1/|T_ctrl|)·Σ 1[chosen_entity≠ground_truth_entity]`。
- **CE** = `(CB_B0 − CB_sys)/CB_B0 · (acc_sys/acc_B0)`。第一项是相对 B0 无状态系统的澄清减少率；第二项是准确率保持率。若 `CE>0`，表示在不损失准确率的前提下减少了提问次数。若 B0 从不澄清，则改用 B1 作为参照，并明确报告这一点。
- **UC** 在纠正类任务（A2、A5、B4、D 系列）上统计：满足 `old.status∈{superseded, expired} ∧ new_memory∈R_s` 的后续任务比例。
- **ECE** = `Σ_b (|B_b|/n)·|acc(B_b)−conf(B_b)|`，按使用的 top-1 记忆的 `eff_conf` 与二元成功结果进行分桶。
- **DMR** = `#(access_count==0 ∧ age_days>half_life)/#total`，在运行结束时统计（与 §12.1 的 `is_dead` 一致）。
- **RRR** = `#(resampled memories recalled into an active set within next maintenance cycle)/#resampled`。
- **MP**：一条已提交记忆被视为 *helpful*，当且仅当它出现在某个任务的 `R_s` 中，并且 `MemoryUsageEvent.contribution=="helpful"` 且 `outcome=="success"`。这里 `contribution` 由 **确定性的 usage-tracker** 标注，而不是 LLM：若它进入所选计划的 grounding set 且验证后的状态与意图一致，则为 `helpful`；若它进入 grounding set 但验证在该 grounding 属性上失败，则为 `misleading`；否则为 `neutral`。因此 `MP = #helpful / #committed`。
- **成本项**：直接读取 `*_latency_ms`、`prompt_tokens` 和 maintenance log。
- **RQ5 代理指标**：CB 来自 `clarification_turns`；UAA 来自安全任务上的 `safety_gated==true`；PM 来自 `chosen_action` 与标注的 `preferred_action` 比较。

### 8.6 统计协议

- **主要指标（§8.1）：每个场景 N≥30** 次运行（不同 seeds）。**次要指标（§8.2–§8.4）：N≥20。**
  主要指标需要更高的 N，以避免多重比较校正把真实但较小的效应全部压平。
- 报告 **均值 ± 95% 置信区间**；系统间比较使用 paired bootstrap 或 Wilcoxon signed-rank。
- 预先声明 **主要 / 次要指标层级**；在每个层级内应用 **Holm 校正**，而不是对全部约 16 个指标做统一 Bonferroni（后者会过度保守）。
- 报告 **效应量（Cohen's d）**，不能只给 p-value。
- 在完整测试套件运行前，冻结 §8.5 的所有公式（防止指标投机）。

## 9. Planner 模式：Oracle vs Agent

**问题。** TSR 同时受两部分影响：
(a) 记忆子系统；
(b) planner 的推理能力。
即使固定同一个 LLM 能保证系统间公平，也无法防止 planner 噪声淹没记忆信号。

**解决方案。** 使用两种 planner 模式；每个场景按 §5 标注的模式执行。

| 模式 | Planner | 测量内容 | 用途 |
| --- | --- | --- | --- |
| **Oracle** | 基于 §8.3-v4 检索包的确定性规则规划器；只要记忆正确就一定能规划正确；不使用自由形式 LLM。Planner 噪声 = 0。 | 纯粹的记忆质量：召回、消歧、状态更新、过期。 | RQ1–RQ4（主要归因） |
| **Agent** | 完整 LLM planner（对同一检索包进行自由形式推理）。 | 在真实噪声下的端到端行为。 | RQ5（端到端） |

**Oracle planner 合约**（确定性、无采样）：
- 输入：§8.3-v4 package（`candidate_devices`、`global_constraints`、`should_ask_user`、各种阈值）。
- 规则：若 top-1 候选分数达到 §6.4-v4 对应任务类型的阈值，且 top1–top2 差距超过歧义边界，则选择 top-1；否则发起澄清；将 `global_constraints` 作为硬过滤条件；绝不凭空创造包外实体。只要给定同一 package，输出必然可复现。

**成本 / 优先级。** 高保真 oracle planner 是整套系统里最重的一项。RQ1–RQ4 一开始也可以先在 agent planner 下报告（N≥30 的均值可平滑一部分噪声）；而 oracle 运行则是更干净的确认性结果，用来回答“问题出在 LLM 还是记忆？”——非常推荐用于 camera-ready，但不是 Phase 8 之前的硬阻塞项。

## 10. 世界模型与 HA Oracle 协议

世界模型是一个 **冻结的版本化工件**（`wm-v1`，见 §4）。所有系统都加载同一个世界。其内容即 §4 中的房间、实体、能力、服务模式、计划变更和失败注入。对外暴露确定性接口：

```text
world.get_registry(t)        # 仿真时间 t 的权威设备 / 实体 / 能力快照
world.get_state(entity, t)   # 当前状态（仅感知；不是长期记忆）
world.apply(service,args,t)  # 通过状态转移 + 失败注入返回 (success|failure, state_delta)
world.events_between(t0,t1)  # 窗口内的注册表变化 + 计划失败事件
```

注册表是设备存在性、实体绑定和服务模式的 **权威来源**（v4 §7.2）。G3 按此规则评分。`simulated_clock.py` 推进虚拟时间，从而让半衰期 / 过期逻辑可即时触发。世界模型序列化为 `world_model/v1.json`，并且其版本固定；每条 trace 都记录 `world_version`；任何场景都只能引用其绑定世界中存在的实体。

## 11. 执行 Trace 模式

按任务与按检索步骤记录；它是 §8.5 中所有指标的唯一数据来源。每条检索到的记忆的动态值位于 `retrieved_memories[]` 中。

```python
class RetrievedMemory(BaseModel):
    memory_id: str
    memory_type: str
    rank: int
    retrieval_score: float             # v4 §8.2 组合分数
    effective_confidence: float        # v4 §5.2，检索时重算
    memory_worth: float                # v4 §6.3
    raw_confidence: float
    system_status: str                 # 系统赋予的状态
    true_status: str                   # 仿真时间下的真实状态（用于 SRR）
    in_usable_set: bool                # 通过 StatusFilter，可被 planner 使用
    in_grounding_set: bool             # 是否实际用于 grounding 所选动作

class RetrievalStep(BaseModel):
    step_id: str
    stage: Literal["device_filter","constraint_filter","planning","execution","verification"]
    query: str
    retrieved_memories: list[RetrievedMemory]
    retrieval_latency_ms: float

class TaskTrace(BaseModel):
    task_id: str
    scenario_id: str
    seed: int
    world_version: str                 # 固定世界（wm-v1）
    planner_mode: Literal["oracle","agent"]
    sim_time: datetime
    system_id: str                     # B0..B5 / Ours / ablation id
    steps: list[RetrievalStep]
    chosen_action: dict | None         # {service, entity_id, args} 或 None
    clarification_turns: int
    should_ask_user: bool
    final_device_state: dict           # TSR
    ground_truth_state: dict
    ground_truth_entity: str | None    # WDR
    preferred_action: dict | None      # PM (RQ5)
    usage_events: list[dict]           # v4 §10.1 MemoryUsageEvent
    memory_status_after: dict          # {memory_id: status} post-task (UC)
    outcome: Literal["success","partial_success","failure"]
    end_to_end_latency_ms: float
    prompt_tokens: int
    safety_relevant: bool
    safety_gated: bool                 # 是否正确要求确认（UAA）
```

指标映射关系：
TSR↔`final_device_state/ground_truth_state`；
SRR↔可用集合上的 `RetrievedMemory.true_status`；
WDR↔`chosen_action.entity_id/ground_truth_entity`；
CE / CB↔`clarification_turns` + TSR；
UC↔`memory_status_after` + 纠正后任务的 `in_usable_set`；
ECE↔top-1 `effective_confidence` + `outcome`；
MP↔`usage_events.contribution` + `outcome`；
成本↔`*_latency_ms` / `prompt_tokens`；
UAA↔`safety_gated`；
PM↔`preferred_action`。
