# 实验方案落地实施蓝图

## 1. 文档目的

本文档用于把 [实验方案-v3(1)-中文翻译.md](./实验方案-v3(1)-中文翻译.md) 和 [师兄写的记忆实现方案.md](./师兄写的记忆实现方案.md) 转化为一份可直接指导工程实现的实施规格书。

目标不是复述实验方案，而是明确：

- 当前仓库已经具备哪些能力
- 当前仓库还欠缺哪些关键能力
- 后续实现应采用什么主线架构
- 每个子系统需要实现到什么程度
- 最终需要产出哪些代码、数据、结果与交付物

本文档面向直接补代码的工程实现者。原则上，实现者应仅依赖本文档与仓库现有代码，即可补齐实验方案所需的主要基础设施与数据链路。

## 2. 目标与范围

### 2.1 最终目标

围绕实验方案构建一套完整、可复现、可扩展的实验基础设施，使仓库能够：

1. 运行冻结世界模型 `wm-v1`
2. 执行 36 个确定性场景脚本
3. 同时支持 oracle planner 与 agent planner
4. 对不同系统配置、基线、消融进行批量实验
5. 输出标准 trace、指标、统计结果与论文表图输入数据

### 2.2 本文档覆盖范围

本文档覆盖以下待实现内容：

- 记忆核心实现回收至仓库内
- 实验虚拟环境与冻结世界模型
- 场景脚本与真值标注
- oracle planner 与 agent planner 双路径
- runner、trace、metrics、results 主线
- baseline 与 ablation 执行框架
- 论文交付物的数据产出链路

### 2.3 不在本阶段直接完成的内容

以下内容可在实施文档中定义接口与预留点，但不要求第一阶段全部完成：

- 真实 Home Assistant 线上环境全量回放
- 真实用户日志驱动的半衰期校准
- 所有图表最终视觉美化
- 高可用部署、服务化封装与多人并发运行平台

## 4. 实施总原则

### 4.1 采用并行实验主线

后续实现采用“并行实验主线”方案：

- 新建 `experiments/` 目录承接实验体系
- 不在第一阶段直接重构 `smartHome/m_agent` 现有主链路
- 通过适配层复用现有 agent、工具和 fake HA 能力

这样可以避免：

- 旧业务链路与新实验链路耦合过重
- 现有回归测试被论文实验逻辑污染
- 难以区分“生产型 agent 代码”和“研究型实验代码”

### 4.2 核心记忆实现必须回收到仓库内

`try.memory` 相关能力必须回收到本仓库内，至少应实现：

- `MemoryRecord`
- `MemoryEdge`
- `SearchResultPackage`
- memory service
- confidence
- expiration
- update policy
- maintenance
- usage tracker
- resampling

不允许后续正式实验继续依赖仓库外隐式实现。

### 4.3 旧测试链路仅作为参考与回归

以下旧代码保留，但不作为论文实验主线：

- `smartHome/m_agent/test/test_home_agent_v2/`
- `smartHome/m_agent/memory/runtime_v1.py`

它们的角色是：

- 复用已有经验
- 提供适配思路
- 承担部分基础回归测试

而不是直接承载实验方案的正式执行路径。

## 6. 目标架构与数据流

### 6.1 总体执行链路

实验执行的标准链路应为：

```text
场景脚本
→ 世界模型初始化
→ 记忆系统初始化
→ planner 选择（oracle / agent）
→ 逐步执行 say/event/expect
→ 检索与规划
→ 设备动作或澄清
→ 执行结果写入 trace
→ 记忆回写与 maintenance
→ 指标计算
→ 聚合结果与表图数据
```

### 6.2 子系统职责

#### A. 记忆核心

职责：

- 保存长期记忆事实源
- 建立检索索引
- 执行生命周期管理
- 执行 update / revise / invalidate / split / merge / delete
- 记录执行后正负反馈
- 支持 maintenance 和死记忆治理

输出：

- 检索包 `SearchResultPackage`
- 标准 `MemoryRecord` / `MemoryEdge`
- usage event
- maintenance 结果

#### B. 世界模型

职责：

- 提供冻结设备注册表与能力真值
- 提供确定性设备状态转移
- 提供时间推进
- 提供计划 mutation / failure injection

输出：

- registry snapshot
- entity state
- apply 结果
- world event stream

#### C. 场景与标注

职责：

- 定义每个场景的步骤序列
- 给出 `expect_action`
- 给出 `expect_clarify`
- 给出 `expect_memory`
- 提供场景分类与 RQ 对应关系

#### D. Planner

职责：

- oracle planner：仅根据检索包和规则做确定性决策
- agent planner：通过现有 agent 与 LLM 做真实决策

#### E. Runner

职责：

- 运行单场景 / 批量场景
- 管理 seed
- 切换 baseline / ablation / planner mode
- 生成标准 trace 与结果文件

#### F. Metrics 与交付层

职责：

- 从 trace 计算各项指标
- 聚合结果
- 输出表格与图表输入数据
- 落盘论文交付物

### 7.1.1 记忆核心固定实现规则

本节是正式实验的规范性实现要求。实现者不得自行替换以下公式、阈值和状态规则；如需调参，必须通过版本化系统配置完成，并在主实验开始前冻结。

#### 存储与索引

- canonical store 使用 SQLite，作为唯一事实源。
- 向量索引使用 Chroma，仅保存 `natural_text`、embedding 与用于粗筛的 metadata。
- 任何检索命中必须回查 canonical store 的最新 `status`、时间字段、置信度和删除标记。
- `deleted` 记录必须从 Chroma 移除；`expired`、`superseded`、`archived` 记录不得用于控制动作。
- 当前 HA 状态仅进入 world perception，不得写成长期 `state` 记忆；只有由多次行为或用户陈述形成的稳定规律才可写入长期记忆。

#### 来源初始置信度

| source | 初始 confidence | 写入状态 |
| --- | --- | --- |
| `ha_registry` | 0.95 | `active` |
| `user_correction` | 0.95 | `active` |
| `user_explicit` | 0.90 | `active` |
| `execution_verification` | 0.85 | `active` |
| `ha_state_observation` | 0.80 | 不写入长期记忆 |
| `user_behavior` | 0.65 | `candidate` |
| `llm_inference` | 0.45 | `candidate` |
| `imported_doc` | 0.70 | `candidate`，需来源审查 |

#### 默认半衰期与硬过期

| memory_type | half_life_days | 硬过期条件 |
| --- | ---: | --- |
| `capability` | 180 | registry、entity 或 service schema 改变 |
| `alias` | 365 | 用户改名或设备消失 |
| `location` / `layout_relation` | 365 | 用户移动设备或 registry 绑定变化 |
| `preference` | 180 | 用户撤销或长期行为持续冲突 |
| `habit` | 90 | 新行为证据持续冲突 |
| `routine` | 180 | 用户撤销或失败率超过场景配置阈值 |
| `episode` | 30 | 已被总结为 reflection / procedure 后可归档 |
| `reflection` | 90 | 后续验证无用或被新 reflection 替代 |

#### 有效置信度与 Memory Worth

每次检索和 maintenance 都按以下公式计算：

```text
age_days = now - max(updated_at, observed_at, created_at)
decay = 2 ^ (-age_days / half_life_days)
hit_score = (positive_hits + 1) / (positive_hits + negative_hits + 2)

effective_confidence =
    confidence * decay * (0.7 + 0.3 * hit_score)

memory_worth = hit_score
```

Memory Worth 行为固定为：

| MW 区间 | 行为 |
| --- | --- |
| `> 0.8` | 检索排序提升；半衰期乘以 1.5；安全任务可满足高价值条件，但仍需满足任务阈值 |
| `0.4–0.8` | 标准行为 |
| `0.2–0.4` | 标记 `needs_verification=true`，下次控制前追问或交叉验证 |
| `< 0.2` | `layer=dormant`，进入清理候选 |

#### 生命周期状态机

必须支持以下确定性迁移：

```text
candidate
  ├─ 用户确认、权威来源写入、或达到晋升条件 → active
  └─ 长期未确认 → archived

active
  ├─ effective_confidence < 0.45 → stale
  ├─ 高置信新事实冲突 → conflicted
  ├─ 新版本替代 → superseded
  ├─ hard expiry / valid_until 到期 → expired
  └─ 用户删除 → deleted

stale
  ├─ 重新验证成功 → active
  ├─ 长期未访问 → archived
  └─ 被证伪或被新事实替代 → superseded / expired

conflicted
  ├─ 用户确认其中一条 → 被确认记录 active，另一条 superseded
  └─ 未确认时不得用于控制动作

archived
  ├─ 被重新召回并验证 → active
  └─ 达到清理周期 → deleted
```

`candidate`、`conflicted`、`superseded`、`expired`、`archived`、`deleted` 不得直接驱动控制动作。`stale` 仅可作为查询解释或澄清证据，不得单独触发控制。

#### `usable-stale` 的正式定义

实验方案中的可用集合 `R_s` 使用状态集 `{active, usable-stale}`。为避免不同实现者对 `stale` 是否可用理解不一致，正式口径固定如下：

- `usable-stale` 不是新的持久化状态，而是运行时标签。
- 一条 `status=stale` 的记忆，只有同时满足以下条件时，才能被标记为 `usable-stale`：
  - `effective_confidence >= 0.45`
  - 不处于 `conflicted`、`superseded`、`expired`、`deleted`
  - 当前任务是 `query`，或该记忆仅用于生成澄清问题
- `usable-stale` 允许进入 query 的回答证据集合，也允许进入 control/safety/automation 的澄清证据集合。
- `usable-stale` 不允许单独驱动任何控制动作。
- `usable-stale` 在被执行验证再次证实后，必须迁回 `active`。

因此：

- 对 `SRR` 而言，`R_s` 的判断口径是 `{active, usable-stale}`。
- 对 `TSR/WDR` 而言，直接驱动动作的记忆必须是 `active`。
- 对 `CB/CE` 而言，`usable-stale` 主要用于支持澄清，而不是静默执行。

#### candidate 晋升规则

| memory_type | candidate → active 条件 |
| --- | --- |
| `alias` | 用户明确说明“以后叫它 X” |
| `habit` | 7 天内同类行为出现 3 次，且无反例 |
| `preference` | 用户明确表达，或行为规律后经用户确认 |
| `routine` | 用户明确确认自动化规则 |
| `reflection` | 失败后可 active，但仅影响检索排序，不直接控制设备 |

### 7.1.2 记忆写入、更新与反馈接口

正式 memory service 必须提供以下接口：

```text
memory_search(query, scope, memory_types, task_type, include_stale=False, include_dormant=False)
memory_get(memory_id)
memory_upsert_candidate(candidate_record)
memory_commit(memory_id)
memory_merge(source_ids, merged_record)
memory_revise(old_memory_id, new_record)
memory_invalidate(memory_id, reason)
memory_delete(memory_id, reason)
memory_mark_used(task_id, memory_id, stage)
memory_mark_outcome(task_id, memory_id, contribution, outcome)
memory_maintenance(sim_time)
```

每轮 `say` 后的写入流程固定为：

```text
1. MemoryExtractor 从本轮输入提取候选事实
2. MemoryResolver 确定 scope、memory_type、关联实体与时间字段
3. MemoryMatcher 查找同 scope 且同 subject/predicate 的已有记忆
4. MemoryUpdatePolicy 选择 add_candidate / add_active / merge / revise /
   invalidate / split / delete
5. MemoryWriteGate 校验来源、隐私、风险、schema 完整性和 candidate 规则
6. 原子写入 SQLite canonical store 与 memory_events 审计日志
7. 同步新增、更新或删除 Chroma 索引
```

操作选择规则：

| 操作 | 触发条件 | 必须结果 |
| --- | --- | --- |
| `add_candidate` | 单次行为观察、LLM 推断、外部文档 | 新记录为 `candidate`，不可控制 |
| `add_active` | 用户明确陈述、HA 权威事实 | 新记录为 `active` |
| `revise` | 同一事实被局部修正 | 新记录 active；旧记录 `superseded` 并指向新记录 |
| `invalidate` | 事实不再成立 | 标记 `expired` 或 `superseded`，保留审计 |
| `merge` | 两条记录 object 完全等价且条件完全兼容 | 新记录包含 `merged_from`、证据并集和 `coverage_proof` |
| `split` | 频繁部分匹配或宽泛 object 导致歧义 | 原记录 superseded；创建按实体拆分的细粒度记录和关系边 |
| `delete` | 用户删除请求或隐私清理 | `status=deleted`，从索引移除，审计事件保留 |

冲突与合并规则：

```text
conflict_score =
    0.40 * source_authority
  + 0.30 * effective_confidence
  + 0.20 * recency_score
  + 0.10 * evidence_count_score
```

- `recency_score = 2 ^ (-age_days / half_life_days)`。
- `evidence_count_score = min(1.0, len(evidence_refs) / 3)`。

- `user_correction > user_explicit > user_behavior > llm_inference`。
- 设备存在、实体绑定、服务能力始终以 world registry 为准。
- 偏好、别名、房间叫法以用户明确陈述和用户纠错为最高权威。
- 两条高置信冲突记录进入 `conflicted`，直到用户确认。
- `subject/predicate` 相同但 object 存在子集/超集关系，或 condition 不完全重叠时，禁止 merge；改建 `specializes/generalizes` 边或执行 split。
- merge 缺少 `coverage_proof` 时，maintenance 必须回滚到源记录。

执行反馈规则：

```text
helpful + success:
  positive_hits += 1
  confidence = min(0.99, confidence + 0.04 * (1 - confidence))

misleading + failure:
  negative_hits += 1
  confidence = max(0.01, confidence - 0.20)
  status = stale 或 conflicted
```

- `helpful`：该记忆进入 grounding set，且验证后的状态满足任务意图。
- `misleading`：该记忆进入 grounding set，且验证在其所依据的属性上失败。
- 其他被检索但未用于 grounding 的记录为 `neutral`。
- 用户明确纠错时，旧记录直接 superseded，新记录以 `user_correction` 的 0.95 置信度写入。
- 失败或纠错必须写入 reflection，至少包含 `failure_type`、`wrong_assumption`、`corrected_fact`、`affected_memory_ids`、`future_rule`。
- 负向证据沿关系图最多传播 2 跳，惩罚为 `direct_penalty * 0.3 ^ distance`；正向命中不得传播。

### 7.1.3 检索、门控与 planner 证据包

检索流程必须按下列顺序执行：

```text
1. TaskAnalyzer 解析任务类型：query / control / safety / automation
2. ScopeFilter 使用 world registry 和 capability 作为硬过滤
3. LayerFilter：优先 active；仅当 active 不足时允许 dormant 作为查询补充
4. ContextRetriever 检索 alias/location/preference/routine/reflection
5. CanonicalRefresh 回查最新 status、时间有效性和删除状态
6. TemporalConfidenceFilter 计算 effective_confidence 与 MW，并应用阈值
7. EvidenceRanker 排序，构造 SearchResultPackage
8. AmbiguityGate 决定执行、保守动作或澄清
```

排序公式固定为：

```text
retrieval_score =
    0.30 * semantic_relevance
  + 0.20 * scope_match
  + 0.20 * effective_confidence
  + 0.10 * recency_score
  + 0.10 * importance
  + 0.10 * memory_worth
```

各子项必须归一化到 `[0, 1]`，计算口径固定为：

- `semantic_relevance = max(0, 1 - chroma_cosine_distance / 2)`；vector index 必须使用 cosine distance。
- `scope_match`：entity 精确匹配为 `1.0`，device 精确匹配为 `0.9`，room 匹配为 `0.7`，home/user/routine 全局匹配为 `0.5`，其他为 `0.0`。
- `recency_score = 2 ^ (-age_days / half_life_days)`。
- `importance` 取 `MemoryRecord.importance`；用户明确偏好/安全规则默认 `0.8`，routine 默认 `0.7`，其他默认 `0.5`。
- `memory_worth` 取 7.1.1 中的 `hit_score`。

任务阈值固定为：

| task_type | effective_confidence 阈值 | 阈值不足时 |
| --- | ---: | --- |
| `query` | 0.45 | 可回答，但必须标注不确定性 |
| `control` | 0.70 | 发起澄清或不执行 |
| `safety` | 0.85 | 必须确认，除非场景明确允许高 MW 直接使用 |
| `automation` | 0.85 | 必须确认触发条件和退出条件 |

歧义门默认使用 `ambiguity_margin=0.10`，并写入版本化 system configuration：

- top1 低于任务阈值时 `should_ask_user=true`
- top1 与 top2 的 score 差小于 0.10 时 `should_ask_user=true`
- candidate、conflicted、expired、superseded、archived、deleted 记录不得进入可执行集合
- registry 与记忆冲突时 registry 胜出

返回给 planner 的 `SearchResultPackage` 必须包括：

- `candidate_devices`：设备 ID、名称、score、confidence、matched memories、missing_info
- `global_constraints`：偏好、约束、routine、reflection
- `should_ask_user`
- `ask_reason`
- `threshold_used`
- `retrieval_metadata`：检索版本、世界版本、时间、过滤原因

oracle planner 只能读取该 package 和 world registry，按阈值与歧义规则确定动作或澄清，不得读取 scenario ground truth。agent planner 使用同一 package 作为上下文，但由 LLM 决策。

### 7.1.4 Maintenance 与失活记忆治理

正式场景执行中，maintenance 只在以下时点运行：

- 场景脚本显式声明 `maintenance` event 时
- 每个任务完成并写入 usage outcome 后

不得在正式评测中隐式加入未记录的随机 maintenance，以保证可复现。

每次 maintenance 按固定顺序执行：

```text
1. 应用 registry mutation，并处理 hard expiry
2. 检查 valid_from / valid_until / expires_at
3. 计算 effective_confidence，执行 active → stale 等状态迁移
4. 扫描高置信冲突
5. 执行可安全合并的重复记录；缺 coverage_proof 时回滚
6. 执行 dead-memory detection、resampling 或 content aging
7. 执行容量清理与 needs_review 标记
8. 刷新 vector index
9. 写入 MaintenanceTrace
```

死记忆判定与处置：

```text
is_dead =
    (access_count == 0 AND age_days > half_life_days)
 OR (last_accessed_at is None AND age_days > 2 * half_life_days)
```

- 如果 `natural_text` 模糊、与同类条目区分度低，则用 `structured_payload + 关联记忆` 重写 description/tags，设置 `resampled=true` 并重置 `last_accessed_at`。
- 重采样后在下一个 maintenance 周期仍未命中时，降级为 dormant。
- 若文本不模糊，则执行 content aging：`layer=dormant`；当 `MW<0.2` 或 `effective_confidence<0.3` 时进入清理候选。
- `sensitive=true` 的清理候选必须改为 `needs_review=true`，不得自动物理删除。

### 7.3.1 Oracle 模式的结构化输入规则

正式 oracle 实验不得使用 LLM 从自然语言临时抽取记忆，也不得由 LLM 判断任务类型或文本模糊度。每个场景脚本必须为每个 `say` / `event` 明确提供以下结构化字段：

```yaml
oracle_input:
  task_type: control
  safety_relevant: false
  memory_ops:
    - op: add_active
      memory_type: alias
      subject: 小书灯
      predicate: refers_to
      object: light.study_desk
      source: user_explicit
  expected_text_quality: specific
```

规则：

- `task_type` 只能为 `query`、`control`、`safety`、`automation`。
- `memory_ops` 是 oracle memory service 的唯一写入输入；它代表已完成的结构化抽取真值。
- `expected_text_quality` 只能为 `fuzzy` 或 `specific`，仅用于死记忆治理；不得在 oracle 路径中调用 LLM entropy 判断。
- 只有 agent planner 路径允许将用户文本送入 LLM planner；agent 路径是否额外启用 LLM extractor 必须由 system config 显式声明，主实验默认关闭，以避免把抽取能力与记忆机制混淆。
- 所有正式场景相互隔离：每个 scenario 从自己的 `initial_memory_fixture`、基础世界状态和 t0 开始，不继承其他 scenario 的 memory/state。

### 7.5.1 版本化运行配置与随机性

每次正式运行必须读取一个 YAML 配置文件，例如 `experiments/configs/main_wm_v1.yaml`。最小配置如下：

```yaml
experiment_id: sae-memory-v4-wm-v1
world_version: wm-v1
scenario_version: sv-v1
system_policy_version: sp-v1
planner_mode: oracle
top_k: 10
ambiguity_margin: 0.10
primary_seeds: [1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008, 1009, 1010,
                1011, 1012, 1013, 1014, 1015, 1016, 1017, 1018, 1019, 1020,
                1021, 1022, 1023, 1024, 1025, 1026, 1027, 1028, 1029, 1030]
secondary_seeds: [1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008, 1009, 1010,
                  1011, 1012, 1013, 1014, 1015, 1016, 1017, 1018, 1019, 1020]
llm:
  source: GLOBALCONFIG
  temperature: 0.0
  max_retries: 0
embedding:
  model: REQUIRED_EXPLICIT_VALUE
  provider: REQUIRED_EXPLICIT_VALUE
  normalize: true
```

规则：

- 配置中的 `embedding.model` 和 `embedding.provider` 必须由运行者显式填写；未填写即拒绝运行，避免不同实验隐式使用不同 embedding。
- oracle planner 不调用 LLM；agent planner 使用从 `GLOBALCONFIG` 解析出的 LLM 名称，并将解析后的 provider/model/temperature 写入 run metadata。
- 主指标使用 30 个 `primary_seeds`；次要指标使用前 20 个 `secondary_seeds`。
- agent planner 不允许自动重试，失败必须写入 trace，避免重试改变采样分布。
- 每次运行将完整 resolved config 复制到结果目录。

### 7.5.2 动作、澄清与状态比较规则

所有 `expect_action` 使用如下标准结构：

```json
{
  "service": "light.turn_on",
  "entity_id": "light.study_desk",
  "args": {"brightness": null, "color_temp": null}
}
```

比较规则：

- `service` 与 `entity_id` 必须精确匹配。
- 未在 `expect_action.args` 指定的字段不参与比较。
- `brightness`、`position`、`temperature` 等数值字段允许绝对误差 `<= 0.01`。
- `expect_action=∅` 时，`chosen_action` 必须为 `null`；任何设备 service 调用均判为失败。
- `expect_clarify=true` 时，trace 必须同时满足 `should_ask_user=true` 且 `clarification_turns>=1`；澄清具体措辞不做 LLM 语义评分。
- `final_device_state` 仅比较真值中列出的 entity/state/attribute 键；未列出的状态不参与 TSR。
- 一个任务包含多个动作时，要求动作集合完整匹配；除 `routine` 明确要求的顺序外，普通独立动作不要求顺序。

### 7.6.1 指标公式与统计规则

所有 metrics 只能从 `TaskTrace`、`MaintenanceTrace` 和场景真值计算；不得用 LLM 充当指标裁判。

设任务集合为 `T`，任务 `t` 的检索步骤集合为 `S_t`，步骤 `s` 的可用记忆集合为 `R_s`：

```text
TSR =
  (1 / |T|) * Σ 1[final_device_state(t) == ground_truth_state(t)]

SRR =
  Σ_t Σ_s 1[存在 m∈R_s，使 true_status(m,t)∈{expired,superseded}]
  / Σ_t |S_t|

WDR =
  (1 / |T_control|) * Σ 1[chosen_entity != ground_truth_entity]

CE =
  ((CB_B0 - CB_sys) / CB_B0) * (accuracy_sys / accuracy_B0)

UC =
  在纠正类场景中，
  1[old.status∈{superseded,expired} 且 new_memory 位于后续 usable set]
  的平均值

ECE =
  Σ_b (|B_b| / n) * |accuracy(B_b) - confidence(B_b)|

DMR =
  #(access_count==0 且 age_days>half_life_days) / #total_memories

RRR =
  #(重采样记录在下一个 maintenance 周期进入 active usable set)
  / #resampled_records

MP =
  #helpful_committed_memories / #committed_memories

Context Efficiency =
  TSR / mean(prompt_tokens) * 1000
```

附加指标固定为：

| 指标 | 计算来源 |
| --- | --- |
| CB | `mean(clarification_turns)` |
| UAA | 安全任务中 `safety_gated=true` 的比例 |
| PM | `chosen_action` 与 `preferred_action` 匹配比例 |
| End-to-end latency | `end_to_end_latency_ms` 的均值/分位数 |
| Retrieval latency | `retrieval_latency_ms` 的均值/分位数 |
| Maintenance cost | `maintenance_latency_ms` 与 `maintenance_tokens` 的日均值 |
| Active Memory Count | 每个 maintenance 后 active/stale 可检索记录数 |

指标实现约束：

- CE 中的 `accuracy_sys` 和 `accuracy_B0` 均等于对应系统的 TSR。
- ECE 使用 10 个等宽 `[0.0, 1.0]` 分桶；每个任务仅使用其最高 rank 且 `in_grounding_set=true` 的记忆。无 grounding memory 的任务不进入 ECE 分母。
- MP 中的 committed memory 是通过 `add_active`、`memory_commit` 或 candidate 晋升首次进入 `active` 的非 registry 记忆；`ha_registry` 基础事实不进入 MP 分母。
- `true_status` 必须由 scenario 真值、world time 和生命周期规则独立重算，不能相信系统自报 `system_status`。
- `helpful` / `misleading` 只能使用 7.1.2 中的确定性 grounding/verification 规则。
- `CB_B0=0` 时，CE 改用 B1 作参照，并在 `metrics.json` 中写入 `ce_reference_system="B1"`。
- Maintenance cost 的日均值等于该 run 的 maintenance latency/tokens 总和除以该 scenario 的仿真经过天数；不足 1 天时除数固定为 1。
- 主指标 TSR/SRR/WDR/CE/UC 使用 30 个 primary seeds；ECE/DMR/RRR/MP/成本/RQ5 proxies 至少使用 20 个 secondary seeds。
- 每个系统比较报告 mean、95% CI、Cohen's d；同一指标层级内使用 Holm 校正。系统成对比较使用 paired bootstrap，若分布不满足要求则使用 Wilcoxon signed-rank。

## 12. Baseline 与 Ablation 落地要求

### 12.1 Baseline

至少实现以下系统配置：

- B0：无记忆
- B1：仅 RAG
- B2：结构化无生命周期
- B3：结构化静态置信度
- B4：全量历史大上下文
- B5：已发表系统类比
- Ours：完整系统

每个 baseline 的行为边界必须冻结为：

| system_id | 必须保留 | 必须关闭 / 替代 |
| --- | --- | --- |
| B0 | world registry、同一 planner | 所有长期记忆与历史检索 |
| B1 | 向量 top-k 检索 | structured schema、生命周期、置信度、治理 |
| B2 | structured record 与基础检索 | 过期、动态置信度、candidate gate、maintenance |
| B3 | structured record、source prior | 半衰期衰减、hits 更新、MW、治理 |
| B4 | 完整原始对话历史 | 检索、结构化记录、生命周期；每轮 prompt 拼接全部历史 |
| B5 | relevance + recency + importance 打分检索 | 过期、版本关系、candidate gate、死记忆治理 |
| Ours | 全部正式 memory core | 无 |

统一要求：

- 相同 world
- 相同场景
- 相同 planner mode
- 相同 LLM / temperature / embedding
- 唯一差异为记忆子系统配置

额外固定参数：

- B1：`top_k=10`，只按 semantic relevance 排序；不得读取 canonical lifecycle 字段。
- B4：每轮 planner prompt 拼接当前 scenario 内从 t0 起的全部原始 user/assistant/tool history，不截断、不摘要、不检索；prompt token 全量计入成本。
- B5：`score = (semantic_relevance + recency_score + importance) / 3`；importance 使用写入时的固定值，不更新 hits，不做候选隔离。
- B0–B5 与 Ours 使用同一个 `top_k=10`、相同 embedding、相同 scenario/world、相同 resolved LLM 配置。

### 12.2 Ablation

至少实现以下消融：

- `-Decay`
- `-AsymFeedback`
- `-Governance`
- `-CandidateGate`
- `-ConflictHandling`
- `-FeatureAbsorption`
- `-Ripple`
- `-Split`

每个 ablation 的关闭边界必须冻结为：

| ablation | 保留完整系统中的其他能力 | 仅关闭的行为 |
| --- | --- | --- |
| `-Decay` | 其余全部 | `effective_confidence=confidence`，不因时间进入 stale |
| `-AsymFeedback` | 其余全部 | `alpha_pos=alpha_neg=0.04` |
| `-Governance` | 其余全部 | dead-memory detection、resampling、content aging |
| `-CandidateGate` | 其余全部 | candidate 可进入可执行集合 |
| `-ConflictHandling` | 其余全部 | 冲突检测，采用新记录覆盖旧记录 |
| `-FeatureAbsorption` | 其余全部 | merge 前子集/超集检查，允许直接 merge |
| `-Ripple` | 其余全部 | 负向关系图惩罚传播 |
| `-Split` | 其余全部 | 自动 split，保留过宽记录 |

统一要求：

- 消融只移除一个组件
- 在 oracle planner 下跑完整场景套件

## 13. 验收标准

实现完成后，至少满足以下标准才算对齐实验方案：

1. 能加载 `wm-v1` 并按仿真时间复现设备变化与失败注入
2. 能运行至少 1 个系统配置 + 36 场景全套并输出标准 `TaskTrace`
3. 能计算以下指标：
   - TSR
   - SRR
   - WDR
   - CE
   - UC
   - ECE
   - DMR
   - RRR
   - MP
   - CB
   - UAA
   - PM
   - latency
   - prompt token
   - Context Efficiency
4. 能同时支持 oracle planner 与 agent planner
5. 能输出支撑表 1–5 与图 1–5 的结构化结果数据
6. 能明确区分：
   - 当前已实现
   - 本阶段待实现
   - 后续增强项

### 13.1 实验完成分级与最小闭环

“能跑”不等于“满足实验方案”。实现完成度按以下三档判定：

| 等级 | 完成条件 | 可得出的结论 |
| --- | --- | --- |
| M0：基础冒烟 | `wm-v1`、一个 Ours 配置、36 场景、oracle planner、标准 trace 可运行 | 证明实验 harness 和 memory core 基本连通；不能回答任何比较型 RQ |
| M1：RQ1–RQ4 实验闭环 | 全部 memory 行为规格、36 场景、oracle planner、对应 metrics、Ours 与 8 个 ablation、主要指标 N≥30 / 次要指标 N≥20 | 可验证过期、更新、校准、治理机制的边际贡献 |
| M2：完整论文实验 | M1 + B0–B5 + agent planner + RQ5 proxies + 成本统计 + 统计检验 + 表 1–5 / 图 1–5 数据 | 可完整回答 RQ1–RQ5，并形成论文实验交付物 |

M0 的“一个系统配置”只用于工程冒烟；不得把 M0 结果描述为实验方案已完成。

### 13.2 最小数据闭环

无论处于哪一级，以下数据链必须完整：

```text
scenario + initial memory fixture + world event
→ retrieval package
→ planner decision
→ world apply / clarify
→ usage outcome + maintenance
→ TaskTrace + MaintenanceTrace
→ metric row
→ aggregate summary
```

如果任意一步没有落盘或无法通过 `run_id + task_id + memory_id` 回溯，则该次实验结果不得用于正式统计。

## 15. 推荐实施优先级

建议严格按以下优先级推进，避免返工：

1. 先回收 memory core
2. 再建 world model
3. 再建 scenario + oracle planner + trace
4. 再接 agent planner
5. 再补 metrics / baseline / ablation
6. 最后整理论文交付物链路

不建议一开始同时并行做以下事项：

- 一边重写 agent，一边构建 experiments 主线
- 一边做复杂图表，一边补底层 trace
- 一边扩展旧 50 用例，一边写正式 36 场景

## 16. 结论

当前仓库已经具备智能家居 agent、demo 记忆适配层、旧测试框架和 fake API 的若干基础，但距离实验方案要求的正式研究基础设施仍有明显缺口。

后续实现必须采用：

- **并行实验主线**
- **核心记忆能力回收到仓库内**
- **旧测试链路仅作参考与回归**

只有在此基础上补齐 `experiments/`、`wm-v1`、36 场景、oracle/agent 双 planner、trace、metrics、baseline、ablation 与结果交付链路，仓库才真正具备服务实验方案、支撑研究问题验证和产出论文交付物的能力。
