# SAE 记忆方案 v3：结构化记忆 + SAE 类比 + 生命周期闭环

> 本方案以 codex 版 v2 为基础骨架，融合 claude 版的 SAE 理论叙事、死记忆检测、容量自适应遗忘等机制，形成可工程落地、可理论解释、可平滑迁移的统一记忆系统设计。

## 0. 设计哲学：SAE 类比

项目名 SAE 取自 Sparse Autoencoder（稀疏自编码器）。SAE 的核心思想为本记忆系统提供统一的理论叙事：记忆不是无限堆叠的文本，而是一个由稀疏激活、过完备字典、死特征检测、特征分裂构成的可演化表示层。

| SAE 概念 | 记忆系统映射 | 对应机制章节 |
|----------|-------------|--------------|
| 稀疏激活 | 选择性检索 — 只有 `effective_confidence` 超过场景阈值的记忆被召回 | §8.1 检索流程、§6.3 使用阈值 |
| 过完备字典 | 记忆条目总量可远超单次需要量，依赖检索筛选 | §11 candidate 隔离、§14 维护任务 |
| 死特征检测 | 死记忆识别 — 长期未激活的条目需重采样或清理 | §14.8 死记忆检测 |
| 特征分裂 | 记忆细化 — 频繁部分匹配时拆分为子条目 | §7 split 操作 |
| L1 惩罚 | 存储压力 — 对总量施加成本，迫使系统精简 | §14.9 容量上限与自适应遗忘 |
| 重建误差 | 信息完整性 — 记忆能准确重建原始知识，否则触发 revise/split | §7 revise/split |
| 特征吸收警告 | 层次合并警告 — 防止隐式信息丢失 | §7.3 merge 警告 |

## 1. 设计目标

当前方案已经把 SAE 的记忆定位为"结构化设备事实 + 可检索知识库 + 运行期辅助规划"，这个方向是对的。新方案不推翻它，而是在现有 `EntityFact` / `DeviceFact`、Chroma 检索、对话 `add/update/delete` 的基础上补齐四个关键能力:

1. **记忆过期**：不是所有记忆都应该永久有效。设备状态、用户习惯、房间布局、别名、自动化规则的稳定性不同，需要不同的有效期和衰减策略。
2. **记忆更新**：不能只靠"最新信息优先"。更新应该区分新增、修正、合并、拆分、取代、失效，并保留旧版本的证据链。
3. **记忆置信度**：记忆被检索出来时，系统不仅要知道"相关不相关"，还要知道"可信不可信""是否过时""是否被验证过"。
4. **容量与死记忆治理**：记忆总量必须受控；长期未访问的记忆要么重采样（重写描述使其可被检索）要么淘汰。

最终目标是让 SAE 的记忆从"可检索文本片段"升级为"可验证、可过期、可演化、容量受控的家庭知识层"，从而更稳定地支持设备选择、意图补全、计划生成和执行后自我修正。

## 2. 调研启发

外部长期记忆系统中有几个共识可以直接迁移到 SAE：

- **Generative Agents** 把记忆流按相关性、近期性和重要性共同排序，并通过 reflection 把零散经验总结成更高层的长期知识。SAE 可以借鉴"相关性 + 最近访问 + 重要性"的召回思想，但要加上智能家居需要的时间有效性和执行可信度。
- **MemGPT / Letta** 强调虚拟上下文管理，把短期上下文和长期外部记忆分层管理。SAE 中也应区分当前状态、长期设备事实、用户偏好、执行经验，避免把所有内容塞进同一种向量库片段。
- **Reflexion** 把失败轨迹总结成 episodic memory，用于下一次尝试。SAE 的执行闭环天然适合在失败后生成"反思记忆"，例如某设备服务不可用、某个推断规则导致错选设备。
- **CoALA / LangGraph memory** 常用 semantic / episodic / procedural memory 分类。SAE 可以把设备事实和偏好看作 semantic memory，把执行轨迹看作 episodic memory，把稳定自动化习惯看作 procedural memory。
- **Zep / Graphiti** 的时间知识图谱思想适合处理"曾经为真、现在失效"的事实。智能家居里位置、设备归属、别名、习惯都可能随时间变化，应该显式记录 `valid_from`、`valid_until`、`invalidated_at`。
- **Mem0** 这类 agent memory 系统强调从对话中动态抽取、合并和检索长期记忆。SAE 需要类似的在线 consolidation，但应该比通用聊天记忆更严格，因为智能家居会实际控制物理设备。
- **FadeMem / SmartVector / Memory Worth** 提供置信度指数衰减、半衰期模型、hits+/hits- 价值追踪机制，本方案的衰减公式与 MW 分级直接借鉴这一脉络。
- **Sparse Autoencoder（项目同名灵感）** 的死特征检测、特征 resampling、L1 惩罚是本方案治理记忆总量的核心比喻。

## 3. 总体架构

新的记忆层仍然围绕 `K_ctx` 展开，但把它拆得更明确：

```text
K_ctx
├── K_fact       设备固有事实：状态、能力、实体绑定、服务 schema
├── K_local      设备局部上下文：别名、位置、房间、设备特定偏好
├── K_global     家庭全局上下文：用户通用偏好、家庭布局、跨设备关系
├── K_episode    执行经验：某次任务中用了哪些记忆、结果是否成功
└── K_procedure  稳定流程：反复出现的场景规则和自动化习惯
```

这五类记忆的生命周期不同：

| 类型 | 例子 | 默认稳定性 | 用途 |
| --- | --- | --- | --- |
| `K_fact` | 设备有哪些实体、能否调亮度 | 高，但受 HA registry 变化影响 | 能力过滤、执行 grounding |
| `K_local` | "小书灯"指书房台灯 | 中高 | 设备 disambiguation |
| `K_global` | 睡觉时全屋灯应关闭 | 中 | 意图补全、规划约束 |
| `K_episode` | 上次卧室门锁执行失败，因为锁芯 jammed | 低到中 | 失败规避、解释和反思 |
| `K_procedure` | "观影模式"=关主灯、开氛围灯、拉窗帘 | 中高 | 复合任务规划 |

关键原则：

- **结构化记录是事实源，向量库只是索引**。Chroma 不应该成为唯一事实存储；它保存用于召回的文本和 metadata，真正的生命周期、置信度、版本关系保存在 canonical store 中。
- **当前状态不进入长期记忆**。例如"客厅灯现在是开着的"只进入运行期 perception，不长期沉淀；除非它形成可复用规律，例如"用户晚上看书时通常把书房灯调到 40% 暖光"。
- **执行前查记忆，执行后反写记忆质量**。每次任务不仅使用记忆，还要记录哪些记忆帮助了任务、哪些记忆误导了任务。
- **总量受控**。每层记忆有目标容量上限，超量触发自适应遗忘，对应 SAE 的 L1 惩罚。

## 4. 记忆条目 schema

建议新增统一的 `MemoryRecord`。`EntityFact` 和 `DeviceFact` 可以作为 payload 的一种，而不是每种事实都单独发明生命周期字段。

```python
class MemoryRecord(BaseModel):
    memory_id: str

    # Scope
    scope: Literal["entity", "device", "room", "user", "home", "routine", "episode"]
    device_id: str | None = None
    entity_id: str | None = None
    room_id: str | None = None
    user_id: str | None = None

    # Type
    memory_type: Literal[
        "state",
        "capability",
        "alias",
        "location",
        "preference",
        "habit",
        "constraint",
        "routine",
        "episode",
        "reflection",
        "layout_relation",
        "safety_rule",
    ]

    # Content
    subject: str
    predicate: str
    object: str
    condition: str | None = None
    action: str | None = None
    natural_text: str
    structured_payload: dict = {}

    # Evidence and source
    source: Literal[
        "ha_registry",
        "ha_state_observation",
        "user_explicit",
        "user_correction",
        "user_behavior",
        "execution_verification",
        "llm_inference",
        "imported_doc",
    ]
    evidence_ids: list[str] = []
    source_turn_id: str | None = None
    source_trace_id: str | None = None

    # Confidence
    confidence: float
    source_authority: float
    importance: float = 0.5
    volatility: Literal["ephemeral", "low", "medium", "high"] = "medium"
    positive_hits: int = 0
    negative_hits: int = 0

    # Time and expiration
    created_at: datetime
    updated_at: datetime
    last_accessed_at: datetime | None = None
    observed_at: datetime | None = None
    valid_from: datetime | None = None
    valid_until: datetime | None = None
    expires_at: datetime | None = None
    half_life_days: int

    # Version and conflict
    status: Literal[
        "candidate",
        "active",
        "stale",
        "conflicted",
        "superseded",
        "expired",
        "archived",
        "deleted",
    ] = "candidate"
    # 正交的 layer 字段：粗粒度分层视图，用于检索时快速过滤
    # status 表达精确生命周期状态，layer 表达存储分层与召回优先级
    layer: Literal["active", "dormant", "archived"] = "active"
    supersedes: list[str] = []
    superseded_by: str | None = None
    conflicts_with: list[str] = []

    # Audit
    access_count: int = 0
    update_count: int = 0
    last_used_task_id: str | None = None
```

`status` vs `layer` 的关系：

```text
status=candidate / active           → layer=active
status=stale / conflicted           → layer=active 或 dormant（取决于 effective_confidence）
status=superseded / expired         → layer=archived
status=deleted                      → 不参与任何检索
```

`layer` 字段对应 SAE 的稀疏激活分级 —— 检索时优先匹配 active 层，dormant 层作为兜底，archived 层只用于审计与解释。

如果短期不想上数据库，可以先用 JSONL 或 SQLite 做 canonical store：

```text
memory_records.jsonl       # 事实源
memory_embeddings/chroma   # 检索索引
memory_events.jsonl        # 追加式审计日志
```

后续再替换成 SQLite/Postgres 也不影响上层接口。

## 5. 记忆过期机制

过期要分成三种，不要混成一个 `delete`：

1. **硬过期**：事实已经不应该再用于执行。例如设备从 HA registry 移除、用户明确说"那个传感器已经拆了"。
2. **软过期**：事实可能仍然有用，但可信度随时间下降。例如"我通常晚上 11 点睡觉"半年后可能不准。
3. **时间窗口失效**：事实只在某段时间有效。例如"这周客厅用空气净化器的夜间模式"。

### 5.1 默认 TTL 和半衰期

| 记忆类型 | 默认半衰期 | 硬过期条件 |
| --- | --- | --- |
| `capability` / `state` | 180 天 | HA registry/entity/service schema 改变 |
| `alias` | 365 天 | 用户明确改名或设备消失 |
| `location` / `layout_relation` | 365 天 | 用户明确移动设备或 HA registry 对应关系变化 |
| `preference` | 180 天 | 用户明确反悔，或长期行为持续相反 |
| `habit` | 90 天 | 新行为证据持续冲突 |
| `routine` | 180 天 | 执行失败率过高或用户撤销 |
| `episode` | 30 天 | 被总结为 reflection/procedure 后可归档 |
| `reflection` | 90 天 | 后续验证无用或被新反思取代 |
| `ha_state_observation` | 不入长期记忆 | 当前状态只走 perception |

### 5.2 有效置信度

检索时不直接用存储的 `confidence`，而是计算当前有效置信度：

```text
age_days = now - max(updated_at, observed_at, created_at)
decay = 2 ^ (-age_days / half_life_days)
hit_score = (positive_hits + 1) / (positive_hits + negative_hits + 2)

effective_confidence =
    confidence * decay * (0.7 + 0.3 * hit_score)
```

解释：

- 时间越久，置信度自然下降。
- 经常被验证正确的记忆下降慢。
- 被证伪过的记忆即使语义相关，也会被降权。

### 5.3 生命周期状态机

```text
candidate
  ├─ 证据足够/用户确认 → active
  └─ 长期未确认 → archived

active
  ├─ effective_confidence < 0.45 → stale
  ├─ 与高置信新事实冲突 → conflicted
  ├─ 被新事实替代 → superseded
  ├─ 超过 hard expires_at → expired
  └─ 用户删除 → deleted

stale
  ├─ 重新验证 → active
  ├─ 长期不用 → archived
  └─ 被证伪 → superseded / expired

conflicted
  ├─ 用户确认其中一条 → active + superseded
  └─ 低风险场景按高置信事实临时使用

archived
  ├─ 被重新召回并验证 → active
  └─ 达到清理周期 → deleted
```

注意：`expired` 和 `archived` 默认不参与执行规划，但可以参与解释和审计。例如用户问"你为什么以前会开这个灯"，系统可以查 archived evidence。

## 6. 置信度机制

### 6.1 来源先验

不同来源的初始置信度不同：

| 来源 | 初始置信度 | 说明 |
| --- | --- | --- |
| `ha_registry` | 0.95 | 设备和实体绑定的权威来源 |
| `user_correction` | 0.95 | 用户纠错优先级最高 |
| `user_explicit` | 0.90 | 用户明确说出的偏好、别名、位置 |
| `execution_verification` | 0.85 | 执行后环境验证得到的结论 |
| `ha_state_observation` | 0.80 | 当前状态可信，但通常不长期保存 |
| `user_behavior` | 0.65 | 从行为推断的习惯，需要多次观察 |
| `llm_inference` | 0.45 | 只作为 candidate，不应直接执行 |
| `imported_doc` | 0.70 | 外部文档，需看来源质量 |

### 6.2 置信度更新

执行后根据结果反写。采用**不对称权重**（一次证伪权重 > 一次验证），对应 Memory Worth 论文的发现：

```text
任务成功且该记忆被用到：
  positive_hits += 1
  α_pos = 0.04
  confidence = min(0.99, confidence + α_pos * (1 - confidence))

任务失败且该记忆直接导致失败：
  negative_hits += 1
  α_neg = 0.20                 # α_neg / α_pos = 5 倍，强不对称
  confidence = max(0.01, confidence - α_neg)
  status = "stale" 或 "conflicted"

用户明确纠错：
  old_memory.status = "superseded"
  old_memory.superseded_by = new_memory.memory_id
  new_memory.confidence = 0.95

只是长期没用：
  不修改原始 confidence
  只通过 effective_confidence 自然衰减
```

### 6.3 Memory Worth（MW）四档分类

`hit_score`（在 §5.2 公式中作为 `hit_score`，等价于 `positive_hits / (positive_hits + negative_hits + ε)`）提供了一个独立的可解释信号。除了在 effective_confidence 里参与计算，还应按四档触发不同操作：

| MW 值 | 分类 | 操作 |
| --- | --- | --- |
| > 0.8 | 高价值 | 提升检索优先级；半衰期 ×1.5 延长；可在高风险场景直接使用 |
| 0.4 – 0.8 | 正常 | 标准检索与执行流程 |
| 0.2 – 0.4 | 可疑 | 标记 `needs_verification`，下次使用前追问或交叉验证 |
| < 0.2 | 低价值 | 降级 `layer=dormant`；进入清理候选名单 |

MW 与 `effective_confidence` 互补：confidence 反映"我们相信它正确的程度"，MW 反映"它历史上是否真的有用"。两者都低才允许丢弃。

### 6.4 使用阈值

不同风险级别使用不同阈值：

| 场景 | 执行阈值 | 低于阈值时 |
| --- | --- | --- |
| 查询型任务 | 0.45 | 标注不确定性即可 |
| 普通控制任务 | 0.70 | 追问或选择保守动作 |
| 安全相关任务 | 0.85 | 必须确认 |
| 自动化/持久任务 | 0.85 | 必须确认触发条件和退出条件 |

例如：

- "床边灯是哪一个？"可以返回低置信候选，并说明"我不太确定"。
- "打开卧室加湿器"需要较高置信度。
- "出门后自动锁门"属于高风险自动化，必须确认。

## 7. 更新机制

现有方案里有 `add/delete/update`，但新方案建议把"更新"细分成七类。

| 操作 | 触发条件 | 行为 |
| --- | --- | --- |
| `add_candidate` | LLM 推断、单次行为观察 | 写入 candidate，不直接用于执行 |
| `add_active` | 用户明确陈述、HA 权威事实 | 写入 active |
| `merge` | 新旧事实兼容，只是补充细节 | 合并 payload，保留 evidence；**触发特征吸收警告检查** |
| `revise` | 同一事实局部修正 | 新版本替代旧版本，旧版本标记 superseded |
| `invalidate` | 事实不再成立 | 标记 expired 或 superseded，不物理删除 |
| `split` | 一条记忆过宽，导致频繁部分匹配 | 拆成多条更细粒度记忆 |
| `delete` | 用户要求删除或隐私清理 | 逻辑删除，并从向量索引移除 |

### 7.1 对话后写入流程

每轮对话结束后执行：

```text
1. MemoryExtractor 从当前对话抽取候选事实
2. MemoryResolver 判断 scope：device/entity/room/user/home/routine
3. MemoryMatcher 查找已有相似或同主语同谓词事实
4. MemoryUpdatePolicy 决定 add/merge/revise/invalidate/split/delete
5. MemoryWriteGate 检查来源、风险、置信度和隐私权限
6. 写 canonical store
7. 同步更新 Chroma 索引 metadata
```

### 7.2 冲突处理

不要简单"最新信息优先"，建议使用：

```text
conflict_score =
    source_authority * 0.40
  + effective_confidence * 0.30
  + recency_score * 0.20
  + evidence_count_score * 0.10
```

处理规则：

- `user_correction` 高于普通 `user_explicit`，高于 `user_behavior`，高于 `llm_inference`。
- HA registry 对"设备是否存在、实体绑定、服务 schema"有最高权威。
- 用户对"偏好、别名、房间叫法"有最高权威。
- 如果两条高置信事实互相冲突，进入 `conflicted`，下次使用前追问。
- 如果低置信 candidate 与 active 冲突，只记录 candidate，不影响执行。

例子：

```text
旧记忆：bedroom_light 位于卧室，confidence=0.90
新输入：用户说"我把那个灯搬到书房了"

结果：
- 旧 location 记忆 status=superseded
- 新 location 记忆 active, confidence=0.95
- 与 bedroom 相关的 alias/clue 记忆降低置信度或进入 stale
```

### 7.3 合并时的特征吸收警告

借鉴 SAE 中"特征吸收"问题：粗粒度特征会吞掉细粒度特征导致信息丢失。`merge` 操作前必须检查：

```text
若两条记忆 M1、M2 满足：
- subject/predicate 相同
- object 存在子集/超集关系（如 "客厅灯" vs "客厅顶灯"）
- 或 condition 不完全重叠

则不能直接 merge。应：
  - 保留两条记忆并建立 specializes/generalizes 关系边
  - 或触发 split：把宽泛的那条拆细
  - 仅在两条 object 完全等价时才允许 merge
```

merge 操作必须记录 `merged_from` 列表与每条源记忆的 `coverage_proof`（合并后能 100% 覆盖原信息），否则 maintenance job 会回滚此次合并。

### 7.4 级联更新

智能家居记忆有关系图，更新一条事实可能影响其他事实：

- 设备位置改变：相关 room clue、routine、layout relation 都要重新评估。
- 设备能力改变：依赖该能力的 routine 降级为 stale。
- 用户偏好改变：相关 habit candidate 降权。
- 执行失败：相关 capability 不一定错，可能是当前状态或服务调用错，需要只惩罚直接相关记忆。

建议用关系字段：

```text
related_memory_ids: list[str]
depends_on_memory_ids: list[str]
derived_from_memory_ids: list[str]
```

涟漪传播仅对**负向证据**触发（hits_negative 增加、被证伪、被 invalidate）。正向 hits 不沿图传播，避免一次成功污染整个邻域：

```text
propagated_penalty = direct_penalty * 0.3 ^ graph_distance
max_distance = 2
direction: only on negative-evidence updates
```

这条规则非常重要：如果正向也传播，会导致一条偏好被验证一次后，整张图都被人为提升 confidence，破坏 hits 信号的诊断价值。

## 8. 检索与规划调用

新检索流程不只返回最相似文本，而是返回"可执行的证据包"。

### 8.1 检索流程

```text
输入：用户任务 Q

1. TaskAnalyzer 判断任务需要哪些记忆类型
   - capability/state
   - alias/location/layout
   - preference/habit/constraint
   - routine/procedure
   - episode/reflection

2. ScopeFilter 先用 HA 和 K_fact 做硬过滤
   - 只保留理论上能执行任务的设备

3. LayerFilter 按 layer 分层召回（对应 SAE 稀疏激活分级）
   - 优先 active 层
   - active 不足时回退到 dormant
   - archived 不参与执行，只用于解释

4. ContextRetriever 查 K_local / K_global
   - 解析"卧室""床边""小书灯""观影模式"等线索

5. TemporalConfidenceFilter 过滤
   - status 必须 active 或可用 stale
   - valid_until 未过期
   - effective_confidence 达到场景阈值

6. EvidenceRanker 排序并返回证据包

7. AmbiguityGate 判断是否追问
   - top1 与 top2 分差太小
   - top1 置信度不足
   - 安全相关动作缺少确认
```

### 8.2 排序公式

```text
retrieval_score =
    0.30 * semantic_relevance
  + 0.20 * scope_match
  + 0.20 * effective_confidence
  + 0.10 * recency_score
  + 0.10 * importance
  + 0.10 * historical_success_rate   # 由 hits 比率（MW）承载
```

注：`historical_success_rate` 即 §6.3 的 MW 信号，区间 [0,1]，由 `(positive_hits + 1) / (positive_hits + negative_hits + 2)` 计算。

不同任务可以调权重：

- 查能力：提高 `K_fact` 和 `scope_match` 权重。
- 查别名/位置：提高 `K_local` 和 `semantic_relevance` 权重。
- 查习惯：提高 `confidence`、`positive_hits` 和 `recency` 权重。
- 查自动化：必须同时满足 routine 条件、约束和安全阈值。

### 8.3 返回给 planner 的结构

不要只给 planner 一段文本，建议返回：

```json
{
  "candidate_devices": [
    {
      "device_id": "device_123",
      "name": "书房台灯",
      "score": 0.86,
      "confidence": 0.91,
      "matched_memories": [
        {
          "memory_id": "mem_alias_001",
          "type": "alias",
          "text": "用户把书房台灯称为小书灯",
          "confidence": 0.95,
          "status": "active",
          "layer": "active"
        }
      ],
      "missing_info": []
    }
  ],
  "global_constraints": [
    {
      "memory_id": "mem_pref_009",
      "text": "用户睡觉时希望全屋灯关闭",
      "confidence": 0.88
    }
  ],
  "should_ask_user": false,
  "ask_reason": null
}
```

Planner 只基于这个 evidence package 做计划，避免把低质量检索片段直接混进 prompt。

## 9. 执行后反馈和反思记忆

SAE 本来就有闭环验证，新方案要把验证结果反写到记忆系统。

### 9.1 每次任务记录 Usage Event

```python
class MemoryUsageEvent(BaseModel):
    task_id: str
    memory_id: str
    used_stage: Literal["device_filter", "constraint_filter", "planning", "execution", "verification"]
    contribution: Literal["helpful", "neutral", "misleading", "unknown"]
    outcome: Literal["success", "partial_success", "failure"]
    verification_delta: float | None = None
    note: str
```

这些 event 用来更新 `positive_hits` / `negative_hits`。

### 9.2 失败后生成 reflection

当执行失败或用户纠错时，生成 `reflection`：

```text
触发：
- 设备选择错误
- 服务调用失败
- 执行后状态未达到目标
- 用户说"不对，不是这个灯"

写入：
- failure_type
- wrong_assumption
- corrected_fact
- affected_memory_ids
- future_rule
```

例子：

```text
wrong_assumption: 把"卧室灯"解析成 ceiling_light，但用户实际指 bedside_lamp。
corrected_fact: 用户说"卧室灯"通常指床头灯，除非明确说顶灯。
future_rule: 下次涉及"卧室灯"时优先检索 bedroom + bedside alias，置信度不足则追问。
```

Reflection 默认进入 `K_episode` 或 `K_procedure`：

- 单次失败：`K_episode/reflection`，半衰期 90 天。
- 多次重复验证：升级为 `K_procedure` 或 active preference。

## 10. 时间知识图谱

建议在 `MemoryRecord` 之上维护轻量关系图：

```text
User --prefers--> warm_light_at_night
Room(bedroom) --contains--> Device(bedside_lamp)
Device(bedside_lamp) --has_entity--> light.bedside
Routine(sleep_mode) --uses--> Device(bedside_lamp)
Preference(warm_light_at_night) --applies_to--> Routine(reading_mode)
```

每条边也带时间和置信度：

```python
class MemoryEdge(BaseModel):
    edge_id: str
    source_id: str
    relation: str
    target_id: str
    confidence: float
    valid_from: datetime | None
    valid_until: datetime | None
    source_memory_id: str
```

好处：

- 房间、设备、别名、routine 的关系可以显式追踪。
- 设备移动后，可以找到受影响的 routine。
- 检索时不仅靠文本相似，还能沿图查找"卧室 -> 床边 -> 台灯 -> entity_id"。
- 旧关系不用删除，只要 `valid_until` 结束，就能解释历史行为。

## 11. 候选记忆隔离

LLM 推断和单次行为观察不能直接变成 active 记忆。建议设置 candidate 层：

```text
candidate 进入 active 的条件：
- 用户明确确认
- 或同类行为重复出现 N 次
- 或执行验证连续成功
- 或 HA registry/状态观测提供权威证据
```

默认阈值：

| 类型 | 升级条件 |
| --- | --- |
| `alias` | 用户明确说"以后叫它 X" |
| `habit` | 7 天内出现 3 次相同行为，且无反例 |
| `preference` | 用户明确表达，或行为规律 + 追问确认 |
| `routine` | 用户确认自动化规则 |
| `reflection` | 失败后即可 active，但只影响检索排序，不直接控制设备 |

这可以避免 agent 因为一次偶然行为就永久记住错误偏好。

## 12. 隐私和安全

智能家居记忆会包含生活习惯，必须有最小化策略：

- **最小保存**：保存任务相关事实，不保存完整聊天原文。
- **敏感标记**：睡眠、出门、安防、门锁、摄像头相关记忆标记 `sensitive=true`。
- **高风险动作确认**：涉及门锁、安防、自动化、远程控制时，提高置信度阈值。
- **用户可删除**：用户说"忘掉这个偏好/不要记住这个"时，执行 `delete` 并从索引移除。
- **防 prompt injection**：从设备名、外部文档、网页导入的文本不能直接作为系统指令，只能作为 quoted evidence。
- **解释可追踪**：执行前或执行后可说明"因为哪些记忆选择了这个设备"。

## 14. 维护任务

建议每次会话开始或每天定时执行：

1. **过期扫描**：处理 `expires_at`、`valid_until`、HA registry 变化。
2. **置信度衰减**：计算 effective confidence，active 低于阈值进入 stale。
3. **冲突扫描**：同 scope、同 subject/predicate 的高冲突事实进入 conflicted。
4. **重复合并**：高相似、同来源、同含义记忆合并（触发 §7.3 特征吸收警告检查）。
5. **死记忆处理**：长期未访问且低置信的记忆归档（见 §14.8）。
6. **索引刷新**：canonical store 变化后同步 Chroma。
7. **评测日志汇总**：统计 stale recall、wrong device selection、clarification turn。
8. **死记忆检测与重采样**（详见 §14.8）。
9. **容量上限与自适应遗忘**（详见 §14.9）。

### 14.8 死记忆检测与重采样

对应 SAE 中的"死特征 resampling"机制 —— 长期不被激活的特征要么删除要么重新初始化。记忆系统同样如此。

**判定条件**：

```text
is_dead = (access_count == 0) AND (age_days > half_life_days)
       OR (last_accessed_at is None AND age_days > 2 * half_life_days)
```

**处理策略**：

```text
1. 描述诊断
   - 检查 description / natural_text 是否过于模糊（语义嵌入 entropy 高、与同类记忆区分度低）
   - 若是 → 进入步骤 2（重采样）
   - 若否 → 进入步骤 3（内容老化）

2. 重采样（resampling）
   - 用 LLM 基于 structured_payload + 关联记忆重写更具体的 description 和 tags
   - 重置 last_accessed_at，给一次新的曝光机会
   - 标记 resampled=True，下次检索时若仍未命中则直接降级

3. 内容老化
   - 降级 layer 为 dormant
   - 若 MW < 0.2 或 effective_confidence < 0.3 → 进入清理候选
   - 若用户曾确认 sensitive=true → 标记 needs_review，由人审核

4. 无法判断
   - 标记 needs_review，进入人工/批量审核队列
```

死记忆重采样是治理"沉睡知识"的关键 —— 很多记忆不是内容差，而是描述不够具体导致检索不上。

### 14.9 容量上限与自适应遗忘（L1 类比）

对应 SAE 的 L1 惩罚 —— 总量必须受成本约束，迫使系统精简。

**目标容量**（可按部署规模调整）：

| Layer | 默认目标容量 | 硬上限（触发强制清理） |
| --- | --- | --- |
| active | ≤ 500 条 | 1000 条 |
| dormant | ≤ 300 条 | 600 条 |
| archived | ≤ 200 条 | 500 条 |

注：与 claude 版的 50/30/20 相比，本方案考虑智能家居场景需保存大量设备事实，把上限调高了一个数量级。

**自适应遗忘阈值**：

```text
对每个 layer 单独计算：
  μ = mean(effective_confidence of all records in layer)
  σ = std(effective_confidence of all records in layer)
  pressure = current_count / target_count       # 1.0 = 刚好达标

  θ_forget = μ - σ * pressure

  若 pressure ≤ 1.0：不主动遗忘
  若 pressure > 1.0：所有 effective_confidence < θ_forget 的记忆降级一层
                    （active → dormant → archived → deleted）
```

直觉：记忆越多，阈值越高，清理越激进；记忆稀少时阈值低，宽容保留。

**保护规则**（即便低于阈值也不能删）：

- `source ∈ {ha_registry, user_correction, user_explicit}` 且无证伪记录
- `sensitive=true` 的记忆只能由用户显式删除
- 被其他活跃 routine/procedure 依赖（出现在 `depends_on_memory_ids` 中）

## 15. 评测方案

在现有 50 个测试用例之外，建议新增记忆生命周期用例。

### 15.1 过期用例

- 用户一周内临时说"客厅灯晚上自动开"，一周后不应继续执行。
- 设备从 HA registry 删除后，相关 capability/location/alias 不再用于规划。
- 当前状态类事实不应被长期复用，例如昨天"门是开的"不能影响今天的门锁任务。

### 15.2 更新用例

- 用户把"卧室灯"从顶灯改指床头灯，旧 alias 被 supersede。
- 用户移动传感器位置，相关 room clue 和 routine 同步更新。
- 用户撤销某个睡眠偏好，旧偏好不再影响后续规划。

### 15.3 置信度用例

- 单次行为推断出的 habit 不能直接用于自动化。
- 多次验证成功的偏好应减少追问。
- 两个候选设备语义相近但置信度差距小，应主动澄清。

### 15.4 闭环反馈用例

- 设备服务调用失败后，相关 reflection 被写入，下次规划避开同一路径。
- 执行成功后，用到的 alias/location 记忆 positive_hits 增加。
- 用户纠错后，误导性记忆 negative_hits 增加并被降级。

### 15.5 死记忆与容量用例（新增）

- 一条 90 天未访问的 alias 应被检测为死记忆，触发重采样或降级。
- 重采样后的记忆若在下个周期被成功召回，应升级回 active 并视为有效 resample。
- active 层超过硬上限时，自适应遗忘应优先清理低 MW + 低 effective_confidence 的记忆，且**绝不清理 ha_registry 来源的核心事实**。
- 特征吸收警告：试图把"客厅灯"与"客厅顶灯"merge 时应触发警告并改为 specializes 关系。

核心指标：

| 指标 | 目的 |
| --- | --- |
| Memory precision | 写入的记忆是否真的有用 |
| Stale recall rate | 过期记忆被错误召回的比例 |
| Wrong-device rate | 因记忆错误导致错选设备的比例 |
| Clarification efficiency | 模糊任务下减少追问但不降低正确率 |
| Update correctness | 用户纠错后旧记忆是否失效 |
| Confidence calibration | 高置信记忆实际成功率是否更高 |
| Dead memory rate | 长期未访问记忆占比；重采样后的复活率 |
| Capacity stability | 各 layer 容量是否稳定在目标范围内 |

## 16. 迁移契约（兼容性原则）

**本方案对现有系统向后兼容**。落地时严格遵守以下契约：

- 现有 `EntityFact` / `DeviceFact` 字段全部保留，作为 `MemoryRecord.structured_payload` 的一种 payload。
- 现有 Chroma 索引继续可用，新 metadata 字段为可选，缺失时用默认值。
- 现有 `add / update / delete` 接口保留，内部映射到新的 `add_active / revise / delete`。
- 现有对话流程不需要立即重写；新功能在第二阶段并入。
- 任何现有记忆数据在首次访问时由 `migrate_legacy_record()` 自动补全缺失字段（confidence / source / layer / half_life_days 等）。

## 17. 最小落地路径

如果要尽快改代码，不建议一次做完图谱和所有策略。可以分三步：

### Phase 1：元数据、过期与 SAE 基础类比

- 引入 `MemoryRecord` schema 与 `migrate_legacy_record()`。
- 给现有记忆补 `confidence/status/layer/created_at/updated_at/half_life_days/source`。
- 检索时过滤 `expired/superseded/deleted`，按 layer 分层召回。
- 实现 `effective_confidence` 与 `memory_worth`。
- 评测：stale recall rate、memory precision。

### Phase 2：更新、执行反馈与死记忆治理

- 把现有 `add/update/delete` 升级为 `add_candidate/merge/revise/invalidate/split`。
- merge 操作加入特征吸收警告检查。
- 执行后记录 `MemoryUsageEvent`，用不对称权重更新 `positive_hits/negative_hits`。
- 用户纠错时标记旧记忆 `superseded`。
- 实现死记忆检测与重采样、自适应遗忘阈值。
- 评测：update correctness、dead memory rate、capacity stability。

### Phase 3：时间图谱、级联和反思

- 建 `MemoryEdge`。
- 支持 room/device/routine 关系传播（仅负向）。
- 失败后生成 reflection，升级为 procedure。
- 增加完整 maintenance job 与生命周期测试集。
- 评测：confidence calibration、wrong-device rate、clarification efficiency。

## 18. 方案总结

新的 SAE 记忆方案可以概括为：

> 以结构化事实为核心，以向量检索为入口，以 SAE 稀疏激活/死特征/L1 惩罚为治理隐喻，以置信度和时间有效性为门控，以执行反馈驱动持续更新。

相比当前方案，新设计多了五个关键闭环：

1. **时间闭环**：记忆会衰减、过期、归档，不会无限期污染规划。
2. **证据闭环**：每条记忆都有来源、证据和版本关系。
3. **执行闭环**：记忆被用过后，会根据执行结果更新可信度（不对称权重）。
4. **冲突闭环**：新旧事实冲突时不是简单覆盖，而是标记、比较、确认、取代。
5. **容量闭环**：死记忆检测 + 自适应遗忘阈值，确保记忆总量受控、低价值条目可被重采样或淘汰。

这能更好地服务 SAE 的核心目标：减少用户重复输入，同时避免 agent 因为陈旧、低置信、或过度堆积的记忆做出错误控制。
